# 返信CLKとDATAの経路分析（2026-11-04）

対象は source `255e5da5a71b551ecb055bdb035dfe0ba433d85d`、実機 FS SHA256 `6c5a10f5c298bc78a8c73bd455247e7f1ea9278880ef055fb8e15d867146658e`。8MHzでCRC不一致、GPIO/1MHzで画素一致した候補の調査であり、高周波動作の適合宣言ではない。

## P4の位相設定の解釈を訂正する

公式 ESP32-P4 revision1.3 TRM Figure 56.5-1（PDF 2817ページ）の経路は次の順序である。

`source MUX → DIV → RX_INV_I → CLK_RX → Gate → RX_INV_O → CLK_RX_out`

[公式TRM](https://documentation.espressif.com/esp32-p4-chip-revision-v1.3_technical_reference_manual_en.pdf) の保存PDF SHA256は `ae1fa2a411776760e03329adc3f9a7c13e98c440168cab208f06e3b2d5818830`。SDK v5.5.2 commit `30aaf64524299d3bde422ca9a2848090d1bc5d0f` の `hal/parlio_types.h` は NEG=0/falling、POS=1/rising と定義し、P4 LL setterは両反転bitを同じ値にする。

|設定|i_inv|o_inv|公式図からの解釈|
|---|---:|---:|---|
|標準NEG|0|0|従来設定|
|標準POS|1|1|内部/外部の相対位相を変え、分周器から外部出力への反転の合成は0|
|過去のiのみ反転試験|1|0|内部と外部出力をともに反転。外部CLKに対する受信位相変更を立証しない|

過去のレジスタreadbackは有効な観測である。しかし「o_inv=0とGPIO matrix不変だから物理出力位相も不変」という解釈は誤りだった。過去の生データを書き換えず、`i=1/o=0` として扱う。既存モデルは両方のサンプル位置を計算したが、その「legacy/inverted」という名前を当該実機試験に直接対応させない。以上は公式図とSDKの解釈であり、pad波形の測定ではない。

## 同じconfigurationのSDF

公式ツールの `gen_sdf` とpost-route Verilog出力だけを追加した再ビルドは、bslib比較で実機FSとconfiguration bitmap（2110×3376）、header/footerが同一だった。出力FSのテキストSHAは `6c469435e12da7d9025a65c1916f4a6e091e5a94f99fc4061ae5588183717ff4` と異なる。元の実機FSは保存し、これを新しい実機実装と扱わない。

`fpga/tools/analyze_output_sdf.py` は公開post-route SDFのIOPATHとINTERCONNECTをグラフ化する。DFFのCLK→Qを始点とし、D→QやRAM経由の架空の組合せ伝播を作らない。組合せ構造上の最長経路であり、論理的sensitizationを検証したSTA pathや実測Tcoではない。最小値はbest corner、最大値はworst corner。

|DATA bit|全serializer制御→pad最大ns|current_word→pad最大ns|metadata_bus→pad最大ns|
|---:|---:|---:|---:|
|0|14.941|9.465|12.049|
|1|14.116|7.973|10.037|
|2|13.278|8.949|10.040|
|3|15.571|9.614|12.838|
|4|15.998|11.128|12.632|
|5|14.161|8.305|10.815|
|6|17.054|9.552|11.907|
|7|16.322|10.086|12.120|

全bitの最長始点はserializer `index_6`。clean clock FF Q→serializer CLKおよびDPB CLKBは共通 best/nom/worst `1.908/2.423/2.937ns`。したがってこのQからpadへの構造上の上限は `2.937+17.054=19.991ns`。IOBUF I→IO自体も `2.183/2.934/3.684ns` であり、過去のモデルのTco=0/2nsは配線・組合せ出力全体を覆っていない。

入力IBUF、sampler位相、216MHz FF Tco、host pad/PCB、P4側capture apertureは別に扱う。これだけで8MHzの不一致やケーブルの原因を確定できない。

再現例（リポジトリrootから）:

```powershell
python fpga/tools/analyze_output_sdf.py fpga/build/clock-filter-output-analysis/filtered_reply/impl/pnr/filtered_reply.sdf --start-contains fast_serializer --output fpga/build/clock-filter-output-delay-fast.json
```

## RAW観測の限界

同一CPU tileに対し8MHz i0/o0は272byte、i1/o0は205byte不一致。全不一致byteは各bitが期待される「直前byteまたは現在byte」の値を採った混合として説明できる。期待CRC trailerは通常offsetに存在し、バイト削除を導入する必要はない。これは遷移近傍の捕捉やskewと整合するが、FPGA出力・P4受信・配線のどれが原因かを識別しない。CRC失敗データを復元して有効応答とする処理は行わない。

実機試験はrootのみ。標準POSの独立候補と同じバイナリによるNEG対照、実際のroute遅延を含む両端タイミング評価が次の判別手段となる。
