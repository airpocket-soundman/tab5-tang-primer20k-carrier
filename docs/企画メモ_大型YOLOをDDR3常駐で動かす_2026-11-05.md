# 企画メモ：Tab5で大型YOLOをFPGAのDDR3常駐で動かす（2026-11-05）

ユーザーとの会話から。**確定した仕様ではなく、企画のメモ。** 数値は概算で、実機・公式資料での検証は未実施。

## 企画

- NPU（ニューラルネットワークのアクセラレータ）ができたら、**一番小さいモデルを動かすのではなく、Tab5のRAMには入らないが、FPGAのDDR3（128MB）には入る大きなYOLO系モデルを、遅くてもよいので動かす。**「Tab5でこんな大きいモデルが動く」ことを見せるのが面白い、という意向。
- 位置づけは**容量のデモ**。速度の勝負ではない。DDR3は透過的なLinuxのメインRAM増設ではなく、明示的なREAD／WRITEで使うデータ領域（`AGENTS.md`）。重みをDDR3に置き、通信は入力画像と結果だけにする。

## 考え方（概算）

| モデル | INT8重み | 概算MAC（640×640） | メモ |
|---|---|---|---|
| YOLOv8 n | 約3MB | 約4 GMAC | 小さい。正しさの確認用 |
| s | 約11MB | 約14 GMAC | |
| m | 約26MB | 約40 GMAC | |
| l | 約43MB | 約80 GMAC | Tab5のPSRAM（32MB）には重みが載らない |
| x | 約68MB | 約130 GMAC | 同上 |

- 公表されているパラメータ数・FLOPsからの概算（再確認していない）。
- FPGAの持続性能を約1〜1.5 GMAC/s（DSP、54MHz、INT8、ピークの2〜3割）と仮定すると、640×640の1枚は n:数秒、s:約10秒、l:約1分、x:約1.5〜2分（概算）。
- P4側は、PIE（SIMD）の1サイクル当たりのINT8積和数が公式の一次資料から取れておらず、未算出。P4の方が速い領域もありうる。

## 必要なもの（現状との差）

- NPUのRTLは部品段階（INT8 MAC、再量子化、ドット積）。畳み込み実行器（im2col／タイリング）、SiLU、アップサンプル、Concat、DDR3アダプタ、モデル変換と量子化が必要。
- **DDR3の利用（READ／WRITE、v1プロトコル）が先**。いまはBISTが実機で通った段階（`docs/引継ぎ_2026-11-04.md` 9章、`DDR3_統合方針メモ_v1案`）。
- 後処理（NMS）はP4のCPUで行う想定。

## 進め方の案

1. 正しさの確認は小さいモデル（n／s）で、CPUのINT8参照と一致させる。
2. DDR3常駐の設計にして、BRAMに収まる前提にしない（モデルサイズに依存しない）。
3. 同じ実行器で、l／xを容量デモとして動かす。

関連：NPU見積もり（`claude/track-o-npu-estimate`、`docs/NPU実現性見積もり.md`）、YOLOのn〜x・DDR3常駐への拡張（`claude/track-o2-yolo-ddr3`、作成中）。

## 優先順位（2026-11-05 の決定）

まずDDR3の「利用」（ホストからのREAD／WRITE）を解決する。NPUはその後。
