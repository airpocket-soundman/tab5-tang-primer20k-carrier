# GPU RX返信クロックの短縮候補（2026-11-05）

## 比較条件

既存all8 v5は216MHzでbus CLKを2段同期し、同じsampled値をもう1tick確認してから
返信CLKを生成する。serializerと色・深度DPBのPort Bは、その同じ返信CLKを使う。
新候補は要求データpipeline・REGISTER_INPUT・全8シーン・ピンを維持し、
`FRAME_TIMING_ENABLE=0` としてフレームcycle計測の追加とは独立に評価する。
この記録は実機試験前のオフライン検証であり、ジャンパ線やP4の入力余裕を保証しない。

## FAST_FILTER_SYNC候補

`reply_clock_filter` と `link_bringup_filtered` に `FAST_FILTER_SYNC=0` を追加した。
既定0は従来の追加1tick確認を維持する。1ではmeta→sampledの2FFを残し、
sampledとqualifiedが異なる時点でqualifiedを更新する。

| 項目 | 従来0 | 新候補1 |
|---|---|---|
| raw→cleanの理論的なデジタル遅延 | 3～4 sample ticks | 2～3 sample ticks |
| 216MHzでの概算 | 13.89～18.52ns | 9.26～13.89ns |
| clean HIGH | 2 sample ticks | 2 sample ticks |
| clean立上り間隔 | 最低5 sample ticks | 最低5 sample ticks |
| meta→sampled | 2FF | 2FF |
| 1sampleだけのHIGH | 拒否 | 通過し得る |

1sample幅の変動をより通しやすくするため、ノイズ除去性能の改善とは扱わない。
短間隔の立上りでfaultを保持する動作、ACTIVE_PIPELINE、非同期reset、
raw DIR・ARMによるOE/READYの即時停止は維持する。

新topは `tab5_dock_speed_filter_top`、ビルドは `fpga/builds/dock/build_speed_filter.tcl`。
ソースと制約をfresh出力内の `source_snapshot` へ固定してから公式Education版でビルドした。

- 出力：`fpga/build/speed-filter-v1/speed_filter/impl/pnr/speed_filter.fs`
- UserCode：`0x8877`
- FS SHA256：`34c5090b91e40cc1165cbf1fb60aaec6b41425cddcaf83a8e3dbd0eaa64553c6`
- 既存のcore54／sampler216／conditioned_reply54制約を使用し、setup/hold違反は各0。
- 最悪slack：setup +0.590ns、hold +0.074ns、recovery +3.251ns、removal +0.892ns。
- 同一domain Fmax：core54 55.775MHz、sampler216 420.408MHz、conditioned_reply54 76.685MHz。
- 限定metadata第一段30組だけの例外を維持。mapped source→stage0→同bit stage1 sole fanoutを再検査した。
- mapped serializer FFと両DPB Port B、計141 clock endpointsは同じ
  `core/clock_conditioner/clean_clk_s1/Q` をsourceに持つ。

### デジタル検証

- 周波数・divider・sample位相90条件で、既定0は固定した旧版72724adの出力波形と一致。
- 各200立上りで候補1は正確に1tick早い。テストのtickは4630psで216MHzの近似値。
- 1sample幅HIGHは候補だけが通過し、近接した2イベントはfaultになることを明示的に確認。
- inactive要求CLK、停止中reset、HIGH幅・cooldownを確認。
- LINK enabled42／disabled27 vectorsで、最大64 records、UPLOAD 640＋380＋4 words、
  CRC不正時の非実行、全tile読戻し、途中ARM解除・復旧に合格。
- 実post-PnR netlistもnative Wire先頭5 recordsと全1024画素・CRCに一致。
  このゲート試験は理想PLL出力・8MHz bus・SDF無しの機能試験であり、実機タイミング証明ではない。

生データは `fpga/build/speed-filter-sync-tests`、`speed-filter-link-tests`、
`speed-filter-gate-tests`、候補の `metadata-proof.json` と `audit.json` に保存した。

## RAW bypassの未合格候補

`REPLY_RAW_BYPASS=0` の既定は従来のfilterを維持する。新RAW topだけを1にし、
serializerと両DPB Port Bを同じraw bus CLKへ直接切り替える候補も作成した。
field/status/CRCの機能試験、共有clock、metadata30組の監査は通ったが、
以下のSTA違反が残ったため実機候補の準備完了とはしない。

| 制約 | setup違反endpoint | hold違反endpoint | 最悪setup | 最悪hold | 最悪recovery |
|---|---:|---:|---:|---:|---:|
| RAW40MHz | 254 | 8 | -14.020ns | -0.218ns | -2.231ns |
| RAW20MHz | 213 | 5 | -12.892ns | -0.165ns | -1.306ns |

主な経路はraw serializer→SYS legacy stream CRC、SYS offer→raw control、
SYS reset_sync→raw async releaseなど。40→20MHzへ下げるだけでは解消しなかった。
SYS CRCを専用データ経路へ分離する、raw reset releaseをそのdomainへ同期する等の
構造整理が必要であり、新しいfalse path／clock groupで隠していない。
RAW40の初期失敗（parameter未反映、unused filter clock制約）もfresh出力のログを保持した。

RAWを測定済み高速版と混同せず、まず小さいFAST_FILTER_SYNC候補を同じhost・TX条件で比較する。
