## 2. 基本ルール（削除してよい条件）

次を**すべて**満たすものだけを削除候補とします。

1. ブランチが `origin/main` にマージ済み（`git merge-base --is-ancestor <branch> origin/main`）
2. ワークツリーの `git status --short` が空（変更・未追跡なし）。ただし、これは`.gitignore`対象が空であることを意味しない
3. 実機成果物・未コミット資料・検証ツール・再生成に必要なローカル設定を棚卸しし、必要物を別の場所へ退避・SHA256照合済み。または、必要なソース・固定IP・ツール版が揃い、再生成可能性を確認済み
4. 管理者（作ったセッション）が、削除に同意している

cherry-pick済みでも祖先判定は未マージになる場合があります。`git cherry -v origin/main <branch>`でパッチ取り込みを補助確認し、単なる未マージ数を「開発中の機能数」と扱わないでください。パッチ同等だけで削除条件1を満たしたことにはせず、履歴の統合または別途保管の扱いを決めます。

ワークツリーを消してもブランチは消えません。ブランチ削除は別操作として扱い、`git branch -d`（マージ済みのみ通る）を使います。`-D` は使わないでください。

## 4. 要確認事項（削除より先に解決）

1. **hostのmain分岐指摘は解消済み。** 現在は両方`e1738e4`、`git rev-list --left-right --count main...origin/main`は`0 0`。一方carrier本体のローカルmainは旧版のまま、基板の未保存変更を保護中。ここをreset/stash/cleanして揃える作業は、このセッションでは行わない。 基板側セッションの作業完了後、管理セッションが未保存変更のコミットまたは退避を確認したうえで、最新の`origin/main`との関係を再確認して揃える。先行して強制resetしない。
2. 実機ビットストリームの参照元を確認する。`docs/モデル常駐_実機手順.md` などが、削除対象のワークツリー内パスを指していないか `grep` で確認し、指していれば現行の再現手順に退避先・対応表を追加します。過去の実測ログやmanifest内の当時のパスは証跡として保持し、一括置換しません。
3. マージ済みローカルブランチ数は調査後に変動しているため、初回の約24本を固定値として使いません。ワークツリー整理の後、`git branch --merged origin/main` で再列挙し、`git branch -d` で消します。リモートブランチの整理は、既存のユーザー指示に基づいて統合済みGPU/MEM関連39本と一時CIブランチを既に整理済み。新たな対象は包含とtip一致を再確認し、今回の文書改訂だけを追加削除の根拠にしません。基板関連ブランチは対象外です。

## 5. 実行手順の提案

1. 対象の`origin`をfetchし、両リポジトリで状態を取り直す。他remoteまで更新する必要がなければ`--all`は不要。状態確認には通常statusに加え、無視対象の成果物・ツールの棚卸しも含める。
2. セクション4の1を再確認する。hostのmain一致は確認済みで、carrier本体の基板作業ツリーは保護する。
3. A群から基板関連・稼働中を除外し、条件を満たすものだけ`git worktree remove <path>`で削除する。実行直前に絶対パスが対象リポジトリの登録済みツリーと一致することを確認する。強制（`--force`）は使わない。拒否されたら中身を確認する。
4. B群の成果物を退避し、退避先でSHA256を照合する。`trackm`は未追跡ビルドログ3件（`fwbuild.log`、`fwbuild2.log`、`fwbuild3.log`）の必要性を確認して保管する。各条件を満たした後に`git worktree remove`を行う。
5. D群はツールの独立配置・成果物検証・参照更新・利用終了を先に確認する。現在の実験ツリーと未包含候補は残す。
6. `git worktree prune` を行い、`git worktree list` で結果を記録する。
7. ブランチ整理は、ワークツリー整理が終わってから別の手順として行う。
