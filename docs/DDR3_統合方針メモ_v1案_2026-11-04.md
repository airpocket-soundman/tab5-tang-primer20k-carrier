## 2. 現状の事実と制約
- 実機：旧IP（サンプル）＋自前BIST（`sampleip_map`）で128MiB全域の書込み・読戻しが1回ずつ合格（5.27秒、約31サイクル／ビート／相）。再生成IP（新ツール）は400MHzで校正が完了しない。旧IPのライセンス条件は未確認。STAのsetup違反は対処中（`docs/DDR3_旧IP採用方針とタイミング対処_2026-11-04.md`）。
- DDR3コントローラIPは暗号化で、USERクロックは約99.5625MHz（memory/4）。LINK PHYはSYS 27MHz系（500kHz以下の初期試験）。クロック間はCDC（ホールド付きバンドル）で結ぶ設計。
- **DDR3は透過的なLinuxメインRAMの増設ではない。** どのホストも明示的なREAD／WRITE系コマンドで使う。
- `AGENTS.md`：ビットストリームは機能別（LINK、GFX、NPU、MEM）で、異なる機能の同時搭載は資源・性能の計測で問題がない組合せだけ。

## 3. 帯域設計メモ
| 区間 | 理論上限（計算） | 実測 | 備考 |
|---|---|---|---|
| DDR3コントローラ（1:4、BL8、DQ16） | 16B×99.5625MHz≈1.593GB/s | **未測定**。BISTは約31サイクル／ビートで約51MB/s相当（帯域測定ではない） | リフレッシュ・行切替で低下。専用エンジンで測る（`docs/DDR3_冷起動_複数seed_soak手順_2026-11-04.md`） |
| 8bit PARLIO（P4⇔FPGA） | 20MHzで20MB/s、40MHzで40MB/s（SDR理論値、プロトコル込みはそれ未満） | GFXの20MHz連続RXで描画は合格（受信）。送信は5MHz級（`85bac224`基準線） | **リンクがボトルネック**：DDR3が約50MB/sでも、ホストから見える帯域はリンクで決まる |
| 表示（FPGA→P4 LCD） | 640×360 RGB565 30fps＝13.8MB/s、1280×720 30fps＝55.3MB/s | 未測定 | 1280×720全面30fpsは8bit 40MHzの理論上限を超えるため基準にしない（MeOS資料） |
| FPGA内部の消費者 | HDMI走査（例：720p60 RGB565＝約110MB/s読出し）、NPU重み（WholeBody 0.6MB／推論）、GFXのフレーム・Zバッファ | 未測定 | 内部消費者はリンクの制約を受けないため、DDR3帯域＋調停が支配的になる |

結論（仮説）：**ホスト経由の転送はリンク律速**で、DDR3は現行BIST速度でも十分。**FPGA内部の消費者（HDMI、NPU）を載せる段階で、DDR3の実帯域と調停が初めて問題になる**。従って帯域エンジンの実測は、内部消費者を載せる前に必須。

## 4. メモリadapter（案）：`mem_adapter`
消費者（LINKのREAD/WRITE、将来のGFX／HDMI／NPU）とコントローラIPの間に置く、USERクロック領域のモジュール。
- **コマンド面**：要求＝`{rw, addr(16B整列、バイト)、len(ビート数)、tag}`、応答＝`{tag, status}`。ready/valid。1要求を、IPの`cmd`／`wr_data`／`rd_data`のペア発行（旧IPのBL8、必要なら`app_burst_number`）に展開。
- **範囲検査**：領域テーブル（base、size、owner）で、範囲外・所有者違い・折返し（`addr+len*16`の広い整数比較）を拒否。実容量は128MiB（旧IPのサンプルが`DDR Size: 1G`と報告）。
- **順序とバリア**：同一消費者内はリクエスト順。消費者間は調停器が決める。**書込み完了通知は、IPがデータを受理してから（DRAM反映は保証せず）**と明記し、READ-after-WRITEの順序は同一adapter内で保証。
- **エラー／タイムアウト**：進行なし（100ms相当）・総時間・校正喪失・読出し順序違反を、既存BIST（`error 1〜9`）と同じ分類で返す。**ジョブ境界でdrain**（未完了のコマンド／データがないことを確認）してから次を受理。タイムアウト後はリセット／再校正が必要（自動再開しない）。
- **CDC**：LINK（SYS 27MHz）→USER（99.56MHz）は、既存の「ホールド付きバンドル＋2段同期＋確認トグル」方式を踏襲。大きなペイロードはBSRAMの非同期FIFO（4KiB×2面）で受け、CRC確認後にコミット。
- **調停**：優先順位は固定優先＋ラウンドロビン。**表示（走査）を最優先**（ライン用BSRAMバッファでアンダーランを防ぐ）、次にGFX／NPU、最下位がLINKのバルク転送。調停の公平性とレイテンシは帯域エンジンの測定後に調整。
- **資源**：現在の`sampleip_map`は論理4984／20736（24%）、レジスタ3950／16173。adapterとBSRAMを加えても、LINK＋MEMの単独ビットストリームには収まる見込み（**GFX／NPU／HDMIとの同居は未測定**）。

## 5. PARLIOのREAD／WRITEコマンドとv1プロトコル（案）

> **2026-11-05追記**：本章のopcode・CRC・チャンク長・取消しなどは `docs/MEMV1_プロトコル仕様_v1確定案_2026-11-05.md` で確定案にした（opcode 0x60〜0x67は他の全opcodeと衝突しないことを確認。実装とRTL試験は完了、実機は未検証）。本章の表は仮案の記録として残す。
既存のLINK（8バイトフレーム、CRC16-CCITT-FALSE、要求ID、タグ付き応答）を土台にする。**opcode番号は仮**で、既存の0x10〜0x44（GFX）と0x50〜0x5c（MEM診断）を避け、`0x60〜0x6f`をv1に仮置き。確定前に全ホストの採用版と照合する。

| 仮opcode | 名前 | 内容 |
|---|---|---|
| 0x60 | `MEMV1_CAPS` | 能力：プロトコル版、容量（バイト）、整列（16B）、最大チャンク（4KiB案）、機能ビット（READ／WRITE／FILL／COPY／CRC32／BIST）、領域数。MEM診断のsignature（0x014d）とは別能力（別signature）にし、旧ホストが誤用しない |
| 0x61 | `MEMV1_STATUS` | 校正、busy、直近エラー、FIFO量、世代（リセットで更新） |
| 0x62 | `MEMV1_RD` | 引数：要求ID（16）、領域／アドレス（32、16B整列）、長さ（ビート数、チャンク上限）。応答：ヘッダ＋ペイロード（長さ×16B）＋ペイロードCRC16（またはCRC32、要決定） |
| 0x63 | `MEMV1_WR` | ヘッダ（要求ID、アドレス、長さ、ペイロードCRC）の後にペイロード。**全チャンクのCRCが通るまでステージングし、通ってからDDR3へコミット**。ACKに要求IDとステータス |
| 0x64 | `MEMV1_FILL` | アドレス、長さ、16Bパターン |
| 0x65 | `MEMV1_COPY` | FPGA内でのDDR3→DDR3コピー（重複領域の向きを仕様化） |
| 0x66 | `MEMV1_CRC32` | 範囲のCRC32をFPGAで計算して返す（Linux側の照合・退避検証用） |
| 0x67 | `MEMV1_CANCEL` | 取消し（部分書込みは巻き戻さない、内容は未定義と通知） |
- **限界・規則**：単一の未完了要求。チャンク上限4KiB（BSRAM 2面のステージング）。長さ0・アドレス非整列・範囲外・折返しは`status=INVALID`。世代を応答に含め、リセット後の古い完了を受理しない。CRC不一致は`CRC_ERROR`で、メモリには書かない。
- **CRCの種類**：リンクはCRC16（既存）。Linux研究側はCRC32を使う。短いペイロードにはCRC16、DDR3の内容検証にはCRC32（`MEMV1_CRC32`）の併用案。**要決定**。
- **ホスト別の適合**：
  - ESP-IDF（Project_B）：フレームバッファ・Zバッファ・モデルのREAD／WRITE／FILL／COPY。既存のTX/RX DMA設計に載せる。
  - Linux：明示的なREAD／WRITE／COPY／FILL。キャラクタ／ブロックデバイス風APIの下層。DMAは未確定のため、最初はGPIO／PARLIO低速でも動く上限付きチャンクにする。
  - MeOS：上限付きバッファ、スケジューラなしのネイティブHAL。応答待ちと取消しのためタイムアウト必須。
- **試験**（MeOS要求の網羅）：不正コマンド、範囲外アクセス、不完全転送、FIFO溢れ、取消し、転送中リセット、CRC不一致。ホスト実装が無いため、まずFPGA側の自己試験（`mem_stage_runner`相当）と、独立したPC側参照実装で確認。

## 6. 矛盾・未確定事項（仕様へ記録）
1. **ビットストリーム分離 vs DDR3共用**：`AGENTS.md`は機能別ビットストリームを求めるが、Project_B（GPU）とMeOSの表示経路はGFXとDDR3の同居を前提にする。→ v1.0はMEM単独（LINK＋adapter）。GFX／HDMI／NPUとの同居は、資源・タイミング・調停の実測後に判断。
2. **旧IPのライセンスと再現性**：旧IP（Gowin製の暗号化生成物）の再配布・同梱条件が未確認で、新ツールの再生成IPは400MHzで校正が通らない。→ 公開物・製品への採用前に確認が必要。取得は固定コミット＋SHA検証（`docs/DDR3_旧IP保管と再現手順_2026-11-04.md`）。
3. **STA**：USER 99.5625MHzでsetup違反が残る（対処中）。BISTの1回合格はタイミング適合の証明にならない。
4. **スケジューラ観測**：旧IPでは出ない。性能問題が出ても内部状態が見えない。
5. **CRCの種類・チャンク長・opcode**：未決（5章）。
6. **帯域**：DDR3内部の帯域は未測定。MeOSの全面30fps要求（55MB/s）はリンク上限を超えるため、v1の目標にしない（ダーティ矩形・FPGAローカル資産が前提）。
7. **ホスト側の実装は、ESP-IDF／Linux／MeOSのいずれにも無い**（本メモ作成時点）。
