# 残り5シーン：compute_simd v2 との突合せとホストABI案

2026-11-04。ブランチ `claude/track-l-scenes`（mainへ未マージ）。前提資料は[汎用SIMD移植設計](残り5シーンの汎用SIMD移植設計_2026-11-04.md)（99728c7）。突合せ相手は `claude/compute-simd` の `2be51bc`（v2、`docs/汎用GPU演算器_v2拡張とGowin配置配線_2026-11-04.md`）。実機・Dock・JTAG・COM4には触れていない。

**この資料の限界：** v2 RTL／`model.py` 上で5シーンを実行しての全画素照合は**していない**（読んで意味を突き合わせただけ）。以下の所要時間は、設計文書のシミュレータ命令数を機械的に換算した目安で、実測ではない。ホスト側リポジトリ（Linux/MeOS/ESP-IDF）の要求との照合も**未実施**で、§5のABIは提案にとどまる。

## 1. 要望ごとの突合せ結果

| 要望（優先） | v2の状態 | 判定 | 注意（意味の差・追従すべき点） |
|---|---|---|---|
| ATOMADD（必須） | opcode 44 `d,[a+imm16]`、`+r[d]`、読み→書き、レーン順直列、戻り値なし | **対応** | 私のDSLも戻り値なしで同じ意味。Galaxyはこれで書ける |
| DIV（必須） | DIV/REM 42/43、0方向切捨て、x/0=-1、約33クロック/レーン直列 | **対応（性能に懸念）** | シミュレータは x/0 で `a` を返す。Flowの除数が0にならない構造かは未精査。移植時にx/0=-1へ合わせて再照合が必要。性能は§3 |
| ブロードキャストload（高） | LDU（45）、レーン0のr[a]でアドレス | **対応** | 私の一様loadは `r0+imm`（アドレスがレーン非依存）なので意味が一致 |
| レジスタ32本／スピル（高） | **未対応**。r2..r14の13本（r0=0, r1=id, r15=述語）。案のみ | **不足（最重要）** | 同時生存の見積り：Particles 7、Galaxy 12／6、Wire 21／19、Fire 27（1オクターブでも20）、Flow 57。13本に収まるのはParticlesとGalaxyのみ |

| 即値形式（高） | ADDI／MULI／LTI（simm16）、ANDI（zero-ext）、SHLI／SARI／SHRI、LUI | **ほぼ対応** | ORI／XORI／EQI／MINI／MAXIなし。Fireの定数（HASH_A/B/M、SX、SY、55706 等）の多くが16bit符号付きに収まらず、LUI+ADDIの2命令＋レジスタ1本になる。命令数・レジスタ圧は設計文書の見積りより悪化 |

| LTU（中） | LTU（36）、LTI（符号付き）はあるがLTUIなし | 対応 | 画面範囲検査は `LTU(x, 640)` に定数レジスタが要る（SIMM16でLTUIがあれば不要） |
| EQ／NE（中） | EQ（37）、NE（38） | 対応 | |
| SEL／MIN／MAX／ABS（中） | SEL（40）、MIN／MAX／ABS（v1） | **対応（形式に差）** | v2のSELは `r[d]≠0 ? r[a] : r[b]` で**条件がdst兼用**。私のDSLは条件が別レジスタなので、移植時に条件のコピー（`ADD d,c,r0`）が1命令増える |

| ISQRT（低） | 未実装 | 不足（低） | Flowの障害物射影のみ（該当レーン約1%） |
| 16bit書込み | STH（byteアドレス、アライン検査） | **対応** | 私の5シーンは1画素1wordで書いている。STHへ変更すると画面書込み量は半分、ただしbyteアドレスとwordアドレスが混在する（§2） |
| ブロックコピー／フィル | 設計のみ（adapter DMA）、RTL未実装 | **不足（中）** | 現状は演算器プログラムで代替（画面クリア＝STOREだけのカーネル、1画素あたりLOAD/STORE各1要求） |
| 広いbaseアドレス | LUI+ADDIで32bit基底を作れるが、**base専用レジスタなし** | **不足（高：レジスタ圧）** | 13本の予算のうち、FB・ACC・TRAIL等の基底がレジスタを食う。v1のbyteアクセスでも同じ |
| 競合STORE順序 | §2.2に明文化（最後に実行されたレーンが勝つ） | 対応 | 私の参照は4レーンのみ検証。2レーン（Gowinで収まる構成）でのWire／Particles／Flowの競合画素は**未検証**で、レーン数別の参照が要る |

要約：**必須の2つ（ATOMADD、DIV）とその他の演算要望は取り込まれた。残る障害は「レジスタ13本」と「base専用の経路」。** Fire・Wire・Flowは、現状のままでは物理レジスタに載らない。

## 2. 追加で見つかったv2固有の問題

1. **ジョブ開始オーバーヘッド**：グループごとに16クロックのCLEARが入る。2レーンなら要素1,000個あたり約8,000クロック（Particlesの8192要素で約65,000クロック）。要素ごとのプログラムが短い（Particles 14.5命令）と、CLEARが実行時間の支配項になりうる。レジスタの初期化が本当に毎グループ必要かは、プログラム側が使う前に書くレジスタだけなら不要。**ジョブごとに「CLEARしない」フラグがあれば良い。**
2. **クロック**：Fmaxの目安は1レーン約43MHz、2レーン約39MHz（ハーネス上、PLL・実ピンなし）。実機で想定できるのは27MHzで2レーンまで。4レーンは未実行。
3. **LOAD/STOREは1要求ずつ・レーン直列**：シミュレータの命令数は「メモリ1クロック」を暗黙にしている。DDR3 adapterの遅延が乗ると、LOAD／STORE比率の高いカーネル（Flowのトレイルコピー、Particlesの画素書込み）が先に律速する。
4. **word／byteアドレスの混在**：LOAD/STOREはword、LDB/LDH/STB/STHはbyte。1画素1halfwordで書くなら画面領域のbaseをbyte単位で別に持つことになり、表（SIN、PAL、RECIP）はwordのまま。プログラムごとに統一ルールを決める必要がある。

## 3. v2で動かした場合の所要時間の目安（実測ではない）

換算：設計文書の（4レーン）群命令数を2レーン用に2倍し、1命令を1〜2クロックと置く（v2の試験で `cycles/instructions` が約2だった例がある。シーンプログラムでは未測定）。CLEAR 16クロック／群と、Flow粒子のDIV（1レーン33クロック×レーン数×粒子あたり約28回）を加える。27MHz、メモリ待ちなし、スピルなし（レジスタが足りる仮定）の**下限に近い**値。

| シーン | 2レーン換算クロック | 27MHzでの1フレーム | コメント |
|---|---|---|---|
| Particles（8192） | 約0.3〜0.5M | 約11〜20 ms | 余裕あり。レジスタ7本で収まる |
| Wire（144） | 約0.5〜1.0M | 約20〜40 ms | レジスタ21本→スピルまたはカーネル分割が要る |
| Galaxy（16384星＋全画素） | 約4.5〜9M | 約0.17〜0.34 s | 星パスとレジスタは収まる。全画素パス（230,400画素）が支配 |
| Flow（8192） | 約14〜22M（DIV約7.6Mを含む） | 約0.5〜0.8 s | レジスタ57本は分割が前提。DIVが全体の約3〜5割 |
| Fire（4オクターブ） | 約45〜92M | 約1.7〜3.4 s | 既存の専用 `fire_pixel.v` に対し、汎用プログラムは1桁以上遅い見込み |

→ Particles・Wireは汎用演算器でそのまま実用域。Galaxy・Flow・Fireは27MHz×2レーンではリアルタイムにならない。**これらは「汎用GPUで動くこと」の実証が目的**で、速度を出すには、レーン増（Gowinでは2レーンまでしか確認していない）、クロック向上、パイプライン化、専用ブロックの併用などの別軸の検討が要る。

## 4. 追加の要望（compute-simd-ext 宛、優先順）

1. **レジスタ拡張（最重要）**：次のどちらか。(a) 命令形式を5bitレジスタに拡張（v2は`imm16`を共有しているので、immを縮めるか、32bit長命令の併用）、(b) **ローカルメモリ（レーンごとBSRAM）＋`LLOAD/LSTORE d,[a+imm]`** によるスピル（レジスタ名の拡張を伴わず、既存の形式のまま入れられる。Gowinの BSRAM は 2レーンで1本しか使っていない）。(b)を推奨。
2. **base専用レジスタ（またはセグメント）**：`LOAD/STORE` に、ジョブごとに設定する数本のbase（FB、作業面、表）を足す。13本の予算を基底に使わないため。
3. **CLEARの省略フラグ（ジョブ単位）**：短いカーネルで16クロック/群の固定費を消す。
4. **ISA形式の不足分**：ORI／XORI／LTUI（またはEQI）、SELの条件を別レジスタにした形式（`SEL d,c,a,b`は4オペランドで入らないので、現形式を維持して構わない。移植側で+1命令を許容する）。
5. **DIV性能**：1レーン約33クロック直列は、Flowで全体の3〜5割。逆数表＋MULSHで代替できる箇所（定数除数など）は私の側でg2として書き換える。変動除数向けに、除算器の複数レーン並列化（面積と相談）または radix-4。**低〜中。**
6. **ブロックフィル／コピーのadapter DMA**：画面クリア、Flowのトレイルコピー（1フレーム数十万要求）、ACC初期化。**中。**
7. **ISQRT**：低。

## 5. メモリ配置と入出力（シーン別）

5シーンは同じ表（SIN、PAL、RECIP など）を共有し、作業面は**必要なシーンだけ**確保する。全域は `fpga/reference/scene_isa_scenes.py` の定数で、現在は1画素1word（RGB565の下位16bit）。単位はすべてwordアドレス。

| 領域 | 開始word | 大きさ（word） | 内容・所有者 |
|---|---|---|---|
| PARAM | 0 | 64 | `[0]=frame`。Flowは渦パラメータを `[16..]` に置く。**ホストが毎フレーム書く** |
| SIN | 64 | 4096 | sin表（Q12）。ホストが一度だけ生成 |
| PAL | 4160 | 256 | パレット（RGB565） |
| FLOWPAL / EDGE | 4416 / 4420 | 4 / 16 | Flowの色、Wireの辺表（頂点番号） |
| RECIP | 4436 | 3072 | 逆数表（Wire 遠近）。`(depth>>3)-512` で引く |
| CUBE / VB | 7508 / 7796 | 288 / 2304 | Wireの立方体中心、変換済み頂点 |
| STAR | 10164 | 3×16384 | Galaxyの星表（`>32767`を跨ぐのでアドレス加算が要る） |
| FB | 131072 | 230400 | 表示面（640×360）。Fireは別途 `FB=65536` の独立配置（`scene_isa_fire.py`） |
| ACC / STATIC / TRAIL | 361472 / 591872 / 822272 | 各230400 | Galaxy蓄積面、静的面、Flowトレイル面 |
| PX / PY | 1052672 / 1060864 | 各8192 | Flow粒子状態 |
| 合計 | — | 1,069,120 | 約4.1 MiB（32bit語）。STHで1画素16bitにすると各面が半分になる |

**FB・ACC・TRAIL・STATIC が131072以降にあり、LOAD/STOREのimm16（±32767）に届かない。**この点が「base専用レジスタ」要望（§4-2）の実際の根拠。

入力：ホストは (1) 表、(2) PARAM、(3) 星表／頂点表／粒子初期値、(4) プログラム（命令列）をアップロード。出力：FB（RGB565）。表示パスは既存のGFX FB→DVI/LINKのどれにするかが未決（§6）。

## 6. フレームの作り方（ジョブ列）

1フレームは次のジョブ列。ジョブは `entry`、`group_base`、`element_count`、`instruction_limit` で指定。ジョブ間でメモリは保持され、命令メモリも保持される（v0 README）。

| シーン | ジョブ列（1フレーム） | element_count |
|---|---|---|
| Particles | ①FBクリア ②粒子 | 230400（クリアはDMA化が望ましい）／8192 |
| Galaxy | ①ACCクリア ②星蓄積（ATOMADD）③全画素合成 | 230400 ／16384／230400 |
| Wire | ①FBクリア ②頂点変換 ③辺描画 | 230400／144／144×16 |
| Flow | ①減衰（トレイル）②粒子（運動＋線描画）③合成（トレイル→FB）④障害物（128×80のタイル） | 230400／8192／230400／10240 |
| Fire | ①画素（4オクターブ） | 230400 |

注意：
- Particles／Wire／Flowの描画系は**書込み競合で結果がレーン数に依存**する（§2.2）。参照は4レーンのみ確認で、2レーン構成の参照は未作成。
- 1フレーム最大4ジョブ。ホスト往復を避けるには**ジョブ連鎖（コマンドバッファ）**が望ましい（§7）。
- ACC／TRAILの初期化と減衰は、現状は全画素のLOAD/STOREカーネル。DMAがあれば不要。

## 7. GPU LAB統合時のホスト側ABI案（提案）

実装も合意もない。まず**ホスト側3リポジトリの要求と照合する**必要があり、本節はその前の叩き台。

1. **能力問合せ**：GFX機能ブロックの能力に `COMPUTE`（レーン数、命令メモリ語数、レジスタ数、ローカルメモリ語数、対応命令群のビット、版）を追加。ホストは版とビットを見て、プログラムを送るかCPUフォールバックにするかを決める。
2. **プログラムのupload**：`PROG_LOAD(slot, addr, words[])`。スロットごとに識別子（ハッシュ）を持ち、同じシーンのプログラムは再ロード不要。ホストは**フレームごとにはプログラムを送らない**。
3. **領域登録**：`REGION_SET(id, base, limit, perm)`。adapterの領域検査と一対一。シーン開始時に1回。
4. **メモリ書込み**：既存のLINKメモリ書込み（表、PARAM、星表）と同じ経路。PARAMの書込みはフレーム境界でatomicにする。
5. **ジョブ実行**：`JOB(entry, group_base, element_count, instruction_limit, base0..3)` を最大4件のリストで一括送信、完了は割込みまたはステータス。途中のジョブがエラーなら以降は実行しない。
6. **ステータス**：`error`（v0のコード表）、`cycles`、`instructions`、`groups`、adapterの `violations`／`timeouts`。ホストはこれをログに出して、性能とエラーを見えるようにする。
7. **安全**：ジョブ前に `flush`、timeoutはホスト設定、リセットで演算器とadapterを同時に初期化（v2 §3.1）。
