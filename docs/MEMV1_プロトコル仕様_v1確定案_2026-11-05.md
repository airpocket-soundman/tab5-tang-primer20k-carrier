# MEMV1 プロトコル仕様 v1 確定案（ホストからのDDR3 READ／WRITE）（2026-11-05）

`docs/DDR3_統合方針メモ_v1案_2026-11-04.md` 5章の仮案を、既存LINK（8バイトフレーム、CRC16-CCITT-FALSE、要求ID、タグ付き応答）に載せる**確定案**に落とした。実装（RTL・Python参照モデル・Cコーデック）とRTLシミュレーションは完了。**実機では未検証**（ホスト側のESP-IDF／Linux／MeOSにも未実装）。DDR3は透過的なLinuxメインRAMの増設ではなく、明示的なREAD／WRITE系コマンドで使う。

**既存opcode（衝突しない範囲）**：LINK 0x01〜0x04、GFX 0x10〜0x16、TRI 0x20〜0x2f、FRACTAL 0x30〜0x3a、TILE 0x3b／0x3c、CORE_CLOCK 0x3d、TRI_BATCH 0x40／0x41、TX診断 0x42〜0x44、triangle_model 0x48〜0x4b（`claude/track-b-fpga`）、edge 0x4c／0x4d（`trackj`のRTL試験でのみ確認、EDGE=0では未対応）、MEM診断 0x50〜0x5c。opcodeのbit7はタグ付き応答（8バイトの0xc3前置）フラグなので、実質7bit（0x00〜0x7f）。

**衝突確認の方法**：(1) 本ブランチのコード（`fpga/host`、`fpga/link/rtl`、`fpga/mem/rtl`）の`8'h`／`7'h`／`0x`、(2) 全リモートブランチ47本の`fpga/host fpga/link fpga/gfx fpga/npu fpga/mem/rtl fpga/tools fpga/platform docs`の`NAME=0xNN`形式とcase定数、(3) 兄弟ワークツリー（`tab5-tang-primer20k-carrier-*`）の同様のgrep。0x5d〜0x7f を opcode として使う箇所は**どこにも無かった**（0x61／0x62／0x63 などは`test_codec.py`の要求ID（seq）値や`0x6d`＝キーボードのI2Cアドレスで、opcodeではない）。静的grepであり、未pushの作業は網羅できない。**他トラックが0x60〜0x67を取る場合は本表を更新して調整する。**

**【2026-11-05 追記：BW測定ブロックとの衝突】** DDR3帯域測定エンジン（`mem_bw_port.v`、ブランチ `claude/membw-sta`、`bcd635e`）は LINK opcode **0x60〜0x6F** を使う（CFG 0x60〜0x6A、START 0x6B、CANCEL 0x6C、SNAPSHOT 0x6D、READ 0x6E、QUERY 0x6F）。これは上表の MEMV1（0x60〜0x67、予約0x68〜0x6f）と**同じ範囲を別の意味で使っている**（例：0x62 は MEMV1 では RD、BW では CFG_COUNT_LO。0x66 は CRC32 と CFG_CTL）。**BWイメージ（`sampleip_map_t4_bw*`）と MEMV1 イメージ（`mem_v1_top`）は別ビットストリームで、同一イメージには同居させない。** ホストは、BWイメージに MEMV1 の要求を送ると CFG 書込みとして解釈され、MEMV1 イメージに BW の要求を送ると別の命令として解釈される（BW CFG の echo と MEMV1 の応答形式は異なるため CRC／形式検査で多くは弾かれるが、保証はしない）。ホストは使用前に必ず能力問合せで識別する：MEMV1 は CAPS(0x60,a=0)=`0x4d31`、BW は QUERY(0x6F,a=0)=`0x0150`（MEMV1 は 0x6F を `UNKNOWN`で拒否）。
**衝突回避案（提案のみ、RTL変更は別トラック）**：BWブロックを未使用の **0x70〜0x7F** へ移す（各 opcode に +0x10。CFG 0x70〜0x7A、START 0x7B、CANCEL 0x7C、SNAPSHOT 0x7D、READ 0x7E、QUERY 0x7F）。0x5d〜0x7f に既存の使用が無いことは本章の衝突確認のとおり、上位16個は16境界で揃うため `opcode[6:4]==3'b111` の1項デコードで済み、`mem_bw_port` の case 定数と `mem_link` のBW振り分けの書換えだけで済む。MEMV1 と BW の両方を載せる合成イメージ（DDR3ネイティブバスの調停が別途必要）も、この移設で opcode 上は成立する。ホスト側は `MEM_BW_FIRST`（`mem_protocol.h`）と `probe_mem_bw.py --op-base` の1か所の値の変更で追従できる（`tab5-fpga-gpu` の `claude/mem-bw-host`）。移設するまでは 0x60〜0x6F が BW イメージ専用。

## 2. フレーム
- 要求8バイト：`a5 op seq 02 a b crcLo crcHi`、応答8バイト：`5a status seq 02 r0 r1 crcLo crcHi`（CRCは先頭6バイト、CRC-16/CCITT-FALSE、下位から）。タグ付き（`op|0x80`）は応答の前に`c3`×8。
- **拡張要求**（RD／WR／CRC32）：ヘッダの`a,b`＝ビート数（le16、1〜256）。続けて**記述子8バイト**`{addr le32, arg le32}`、WRはペイロード（ビート数×16バイト）、最後に**CRC16トレーラ2バイト**（ヘッダ先頭6バイト＋記述子＋ペイロードに対するCRC16、`link_crc16_extend`と同じ連鎖）。`arg`：WR＝ペイロードのCRC32（zlib）、CRC32＝直前の確定CRC32（新規は0）、RD＝0必須。
- **拡張応答**（成功時のみ）：RD＝8バイトヘッダ＋ペイロード＋CRC16（応答先頭6バイト＋ペイロード）、CRC32＝ヘッダ＋crc32(le32)＋CRC16。WR成功は8バイトのみ。いずれも成功時`r0,r1`＝**世代**。**statusが0以外の応答は常に8バイト**。
- ビート数が0または256超のヘッダは、記述子以降を待たずに`INVALID`(3)の8バイト応答を返す（ホストは続きを送らず、方向を切替えて応答を読む）。
- アドレスは**バイトアドレス**、16B整列、容量128MiB（0x0〜0x7ffffff）。1ビートの16バイトのうち、バイトkはDDR3バイトアドレス`base+16*beat+k`に対応（ビート内の下位バイトが先）。
- ホストは要求を1つずつ処理（未完了は最大1つ）。**チャンク上限4KiB（256ビート）**。それ以上はホストが分割する（CRC32は連鎖で継続できる）。再送は自動で行わない。

## 3. status
| 値 | 名前 | 意味 |
|---|---|---|
| 0 | OK | 成功 |
| 1 | FORMAT | ヘッダ形式／CRC不正（従来どおり） |
| 2 | UNKNOWN | 未知opcode、未実装のFILL／COPY |
| 3 | INVALID | 長さ0、257ビート以上、非整列、範囲外、32bit折返し、語番号不正、RDの`arg`≠0 |
| 4 | TIMEOUT | DDR3が進行しない（約81ms相当）。書込み範囲は未定義の可能性 |
| 5 | NOT_READY | 校正未完了、USER側が未起動 |
| 6 | BUSY | BIST実行中、または前の拡張命令がUSER側で未完了 |
| 7 | CRC_ERROR | トレーラCRC16またはペイロードCRC32の不一致（**DDR3へは何も書かない**） |
| 8 | CANCELLED | 取消し（部分書込みあり得る、`r0,r1`＝確実に完了したビート数） |
| 9 | DDR_FAULT | 実行中に校正喪失、読出し順序違反 |
| 10 | STALE | 実行中に世代が変わった（リセット／校正喪失／USERリセット）。応答は捨てる |

検査の優先順位（拡張要求）：ヘッダCRC(1)→ビート数(3)→全受信後にトレーラCRC16(7)→範囲(3)→WRのペイロードCRC32(7)→NOT_READY(5)→BUSY(6)→実行。範囲検査はSYS側とUSER側`mem_adapter`の両方で行う。

## 4. 各命令
- **CAPS(0x60)** `a`=語番号：0=形式`0x4d31`（診断MEMの`0x014d`とは別）、1=版`0x0100`、2=容量MiB(128)、3=整列(16)、4=最大ビート(256)、5=機能ビット（RD1／WR2／FILL4／COPY8／CRC32 16／BIST32／CANCEL64。現状`0x73`）、6=領域数(1)、7=仕様のみの機能（`0x000c`＝FILL／COPY）。他は`INVALID`。
- **STATUS(0x61)** `a`=語番号：0=フラグ（b0校正済、b1 USER起動、b2 USER側で実行中、b3 BIST、b4 取消し／異常終了による**未定義範囲あり**）、1=**世代**、2=直近のstatus、3=完了した拡張命令数、4・5=未定義範囲の開始アドレス(下位・上位)、6=未定義範囲のビート数、7=**生の信号**（b0 pll_lock、b1 controller_reset_n、b2 ip_user_reset、b3 user_reset_n、b4 init_calib_complete、b5 reset_hold==0、b6 user_abort、b7 mailbox epoch完了、b8 USERクロック動作中）。
- **RD(0x62)**：上記の拡張要求。DDR3→読出しバッファ（BSRAM 4KiB）→応答。
- **WR(0x63)**：ペイロードは**ステージング（BSRAM 4KiB）**に受け、**トレーラCRC16とペイロードCRC32が両方通り、範囲検査が通ってから**DDR3へコミットする。応答は「IPがデータを受理した」時点（DRAMへの反映完了は保証しない）。同一adapter内のWR→RDの順序は保たれる。
- **CRC32(0x66)**：範囲をFPGAで読み、`arg`を前値とするCRC32を返す。チャンクを連鎖：`crc32(data, prev)`（zlib）。
- **FILL(0x64)（仕様のみ）**：`a,b`=ビート数、記述子`{addr, 0}`＋パターン16B、トレーラ。8バイト応答。
- **COPY(0x65)（仕様のみ）**：`a,b`=ビート数、記述子`{src, dst}`、トレーラ。範囲が重なる場合は「一時領域経由でコピーした結果」と同じ（memmove）。8バイト応答。
- **CANCEL(0x67)**：実行中の拡張命令があるときだけ意味を持つ。ホストは**方向を切替えず**（DIR=0のまま）要求を打ち切り、`CANCEL`の8バイトを送る。FPGAは次のビート境界で停止し、`CANCEL`の応答を返す（元の命令の応答は返さない）：`status=0`、`r0=1`＝取消した、`r0=2`＝取消し前に完了した。何も実行していないときは`status=0,r0=0`。**書込み途中の取消しは巻き戻さず**、STATUSの未定義範囲（フラグb4、語4〜6）に残る。未定義範囲の記録はリセットまで残り（WRの成功では消えない：ホストが内容を再検証してから扱う）、別の異常終了で上書きされる。

## 5. 世代・リセット・古い完了
世代（16bit）は、SYS側の自由走行カウンタで、(a) `reset_n`／`arm`の立下り、(b) 校正完了の喪失、(c) USERリセットの立下り、のたびに+1（電源投入時のみ0）。各命令のタグ＝`{世代,要求ID}`（24bit）で、USER側からの完了のタグがSYS側で発行したものと一致しなければ**無視**する（リセット中の古い完了、取消し後の遅れた完了）。実行中に世代が変わると`STALE`(10)を返す。リセット後は未完了命令・ステージング・取消し状態はすべて破棄され、リンクの未送信応答も無い。

## 6. 実装構成
- `fpga/mem/rtl/memv1_sys.v`：SYS(27MHz)のLINK＋制御。既存`mem_link`と同じ低速PHYで、legacy op（1〜4、0x50〜0x5c）は挙動不変、0x60〜0x67を追加。ステージングRAMへ書込み、CRC16／CRC32を受信中に計算。
- `fpga/mem/rtl/memv1_bridge.v`：LINK(SYS)→USER(約99.56MHz)の**ホールド付きバンドル**CDC（SYS側がバンドルを保持し、toggleを2段同期、USER側が結果を保持してtoggleを返す）。USERリセット中は現在のtoggleを採用して再生しない。
- `fpga/mem/rtl/mem_adapter.v`：USERクロック領域のadapter（ready/valid、tag、範囲検査、READ／WRITE／CRC32）。ネイティブIF構造は実機で合格した`mem_bist`のPIPELINE=4と同じ（ペア書込み、登録済みwantとIP readyのAND）。
- `fpga/mem/rtl/mem_v1_core.v`：既存`mem_bist`／`mem_mailbox`を**無改変**で再利用し、IP共有は「adapterが動作中はadapter、それ以外はBIST」。`mem_top`／`mem_bist`は**編集していない**（`mem_bw`を`mem_top`へ配線するトラックと衝突しない）。
- `fpga/mem/rtl/mem_v1_top.v`：PLL＋旧IP（Sipeed `DDR3_Memory_Interface_Top`）＋ピン。ポート名は`mem_top`と同じで`mem_bist.cst`をそのまま使う。
- ホスト：`fpga/host/mem_v1.h`（Cコーデック）、`fpga/mem/tests/memv1_model.py`（ビット単位の参照モデルとベクトル生成）、`fpga/tools/memv1_probe.py`（8バイトxfer経由の確認）。

- WRの完了意味（DRAM反映の保証なし）、CRCの併用（CRC16＝リンク、CRC32＝内容）は統合方針メモの「要決定」を本案で決めたもの。Linux研究側の了解は未取得。

## 10. 実機で確認する手順（親セッション用）
前提：Dock＋Core、Tab5ブリッジ（COM4）、`dock-jumper-v0`の配線レビュー済み。リンクは**500kHz以下**（SYS同期PHY）。
1. 書込み前：`fpga/build/memv1/out/mem_bist/impl/pnr/mem_bist.fs`のSHA-256が上表と一致することを確認。**SRAMへのみ**書込む（`openFPGALoader -b tangprimer20k -m <fs>`相当。フラッシュへは書かない。電源断で戻る）。既存の`dock_dev.py program`は`link／gfx／triangle`専用なので、MEM BISTと同じ手順で直接`openFPGALoader`を使う。
2. 起動後約1〜2秒（リセット保持＋校正）待つ。
3. `python fpga/tools/memv1_probe.py --port COM4 --arm`：期待＝`caps.format 0x4d31`、`capacity_mib 128`、`features [RD,WR,CRC32,BIST,CANCEL]`、`status.calibrated true`、`user_alive true`、`legacy_mem_caps 0x14d`。`calibrated false`なら校正が通っていない（旧IP＋同PLLの`sampleip_map_t4`では通った構成なので、まず電源・ピン・DIPを確認）。
4. BIST：`--bist 1024`（16KiB）→`--bist 8388608`（128MiB全域、約5.3秒）で`done true`、`faulted false`、`errors false`。mux経由でも旧BISTが動くことの確認。
5. RD／WR／CRC32の往復：Tab5ブリッジに**長フレームのコマンドが必要**（例：`xferx <要求hex> <応答バイト数>`でFPGA応答をそのまま返す）。ブリッジ拡張後、`mem_v1.h`（または`memv1_model.py`のビルダー）で：(a)1ビートWR→RD→比較、(b)256ビートWR→RD→CRC32比較、(c)範囲外・非整列・長さ0が`INVALID`で、後続RDが元の内容、(d)ペイロード1bit反転が`CRC_ERROR`で後続RDが元の内容、(e)末尾4KiB（0x7fff000）、(f)WR途中のCANCELとSTATUS未定義範囲。ブリッジ拡張がない間は4.まで。
6. 失敗の切り分け：`STATUS`語0（校正／USER起動／BIST）、語1（世代が勝手に増えるならリセット／校正喪失）、語2（直近のstatus）。`status 9`／`10`はDDR3側の異常、`4`は進行しない。
