# Mandelbrot連続DMA失敗の分析(トラックG)

2026-11-04。オフライン解析のみ。実機には触れていない。実機の事実は親セッションの測定(統合main・凍結9029ファーム、FPGA `94458f3b`)による。

## 実機の事実(測定済み)

- ポリゴンは連続DMA 5MHzで全画素一致。MandelbrotはTILE読出しで決定的に失敗し、`dma_last_stage=stream_timeout`、`dma_last_error=263`、`dma_last_bytes=3072`。1MHz・2MHz・5MHz、frame 0/17/403のどれでも同じ。
- GPIO有限RXではMandelbrot・Juliaとも全画素一致。FPGAの演算ロジックは正常。
- Codexは同条件で合格を記録している(`gpu-rx-scaled-5mhz-matrix-2026-11-04.json`)。配線・設定の変更はないとの申告。

## 失敗時の受信窓のデコード(確認済み)

対象は `failed_continuous_window`(seq 37、要求 `a5bb25020000938b`、2048バイト)。

| 位置 | 内容 |
|---|---|
| 0〜112 | `0xcd` 113バイト。DMAが書いていないバッファの初期値 |
| 113〜149 | `0xc3` 37バイト。訓練。仕様の8バイトより長いが、開始前に取り込んだアイドルサンプルで、Codexの合格時も同期オフセットは149〜156で同種 |
| 150〜157 | ヘッダ `5a 00 25 02 00 00 ed 1d`(seq 0x25が要求と一致) |
| 158〜 | RGB565画素。32語/行のMandelbrotの行構造が最初の約8行は正しい |
| 行8付近(語約258) | バイトのずれ(スリップ)が始まる。語 `ffe0 feff fd00…` のように、本来 `ff00 fe00 fd00…` と並ぶパレットが1バイトずれる |
| 語353(ペイロードのバイト706) | `0xFE` が592語(窓の終わりまで)続く |

結論(確認済み): 本体CRCの不一致より前に、**応答データがペイロードの途中で壊れ、その後は定数 `0xFE` になる**。パーサが一意フレームを確定できないのは、受信データ自体が壊れているため。パーサの不具合を示す証拠はない。

## RTL読解(確認済み)と仮説

`fpga/link/rtl/link_reply_raw.v` は `bus_clk`(パッドのCLK)のエッジ数で出力バイトを進める。

- エッジが1本余分に入ると、出力が1バイト先へ飛ぶ(ホストにはバイトの欠落=ずれに見える)。
- タイル語のタグが不一致になると `error<=1; done<=1` となり、`index` が凍結してバスを開放する。以後は未駆動のバスで、ホストには定数が見える。
- 既存の `tb_link_sync` は、READYが応答の間ずっと高いことを確認している。**「READY低下で受信を誤って打ち切る」仮説は、RTLモデルでは否定される。**

### 本トラックの追加試験(`link/tests/run_fractal_clock.py`、RTLシミュレーション)

| 条件 | 結果 |
|---|---|
| 自走クロック1MHz、MandelbrotのTILE_READ | 2066バイトすべて一致 |
| 自走クロック5MHz | すべて一致 |
| 5MHzでバイト900の後に余分なエッジを1本 | バイト901から不一致。シリアライザは打切らず、最後まで出力する |

- 確認できたこと: 余分なエッジ1本で「バイトのずれ」の症状は再現する。
- 確認できなかったこと: `0xFE` 固定(打切り)は、1本の余分なエッジでは再現しない。実機の署名との完全な一致ではない。

### 仮説(未確認)

1. **H1: CLKに余分なエッジが載っている(グリッチ、リンギング、クロストーク)。** FPGAの `link_reply_raw` はパッドのCLKを直接クロックに使い、グリッチフィルタを通さない。Mandelbrotはデータのビット遷移が多く、フラットなポリゴンより干渉を受けやすい。GPIO受信が通る理由は、エッジの立上がり特性やクロック幅が異なる可能性がある。
2. **H2: 打切りは複数の余分なエッジ、またはエッジの欠落が重なったときに起こる。** 単発では打切られない(上記試験)。
3. **H3: ホストが開始前にCLKを接続していることによる、先頭サンプルのずれ。** 37個の `c3` の説明にはなるが、データの途中の崩れは説明しない。

## 実機で1変数ずつ確認する手順

前提: 同じTab5ファーム(統合main)、同じ条件(5MHz、シーン2、frame 17)。

1. **FPGAイメージだけを変える**: クロックフィルタ版(`filtered_reply.fs`、SHA `6c5a10f5…`、USERCODE `0x7D1F`)を書き込み、Mandelbrotが通るかを見る。通れば、H1(CLKのグリッチ)が有力。フィルタ版は `reply_clock_filter.v` が216MHzでCLKを整形する設計。
2. 通らない場合は、**CLKの駆動強度だけを変える**(最弱・既定・強)。強い駆動は悪化する記録がある。
3. **CLK線の直列抵抗だけを変える**(33→47→100Ω)。エッジの鈍らせ。
4. **データパターンだけを変える**: 同じ周波数で、シーン1(ポリゴン)とシーン2を比べる。さらに、遷移の多い固定パターンを返す診断(TILEにテストパターンを読み出す)があれば最も明快。
5. **FPGAの診断カウンタ**: 応答ごとのCLKエッジ数を読み出し、期待値(2066)と比べる。RTLに診断カウンタの追加が必要(未実装)。

## 未検証
