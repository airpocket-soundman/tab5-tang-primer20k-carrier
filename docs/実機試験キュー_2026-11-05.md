### 優先度の根拠と、試す価値・危険

- **共通の危険**：FPGAイメージはSRAMのみで、電源断か再書込みで消える。SPI flashには書かない（`--operation_index 2`）。Dock側の部品に不可逆な変更はない。書込み前に Tab5 を `disarm`、ホストを `stop` にする。N のイメージは応答クロックの遅延でOE/READY解除が遅れる性質があり、ターンアラウンドでバス衝突の恐れがある（シミュレーションのみの知見、実機未確認）。衝突が疑われる症状が出たらそのtick以上は試さない。
- **J（1番）**：25MHz失敗が仮説A（受信窓）かB（余分なCLKエッジ）かの決め手。ただし216MHz標本化のため、4.63ns未満のパルスは見えない（アナログ測定ではない）。まず20MHz合格点でモニタ自体が健全か（excess等がゼロか）を確認する。N は J の結果が出てから（Nの文書も同じ順を推奨）。
- **N（2番）**：位相で合格帯が動くかで仮説Aを検証。J の結果が「エッジ数正常」のときに価値が高い。REPLY_FINE_DLY（IODELAY）変種は未ビルド。
- **B（3番）**：ポリゴンのCPU比を縮める本命。深度の向きで裏面が表に出る問題は未解決（CPUと同じ深度なので全画素比較は成立）。性能向上は実測まで主張しない。
- **I（4番）**：ホストのみ。見積りでは描画の約2〜4%にとどまる。FPGAは基準線で足りる。
- **P2（5番）**：t4 は STA 上の見た目が良いだけで、診断用SDC下の結果。実機で `sampleip_map`（段階3を1回合格）と同じ結果が出るか、1ビートごとのアイドル追加などの影響がないかの確認が目的。DDR3は透過的なLinuxメインRAM増設ではない。

## 2. 共通コマンド

作業ディレクトリは、`programmer_cli` は `fpga/build/tools/gowin-programmer-1.9.12.04/`、比較はホスト `tab5-fpga-gpu` 側。

### FPGAのSRAM書込みとUSERCODE確認（可逆）

```
programmer_cli.exe --scan-cables
programmer_cli.exe --device GW2A-18C --operation_index 2  --cable-index 1 --frequency 2.5MHz --fsFile D:\esp\images\<名前>\<名前>.fs
programmer_cli.exe --device GW2A-18C --operation_index 73 --cable-index 1 --frequency 2.5MHz   # USERCODE
programmer_cli.exe --device GW2A-18C --operation_index 74 --cable-index 1 --frequency 2.5MHz   # Status（0x6020が正常）
```

cable-index は 1（0は「failed to open」）。書込み直後の「Error found!」は既知で、USERCODE・Statusが一致すれば読戻しは正しい。USERCODE が上表と一致しなければ、先に進まない。

### ホストファームの書込み

```
python -m esptool --chip esp32p4 -p COM4 -b 460800 --before default_reset --after hard_reset write_flash "@flash_args"   # ビルドディレクトリで
```

ビルド：`powershell -File tools\build_dock_demo.ps1 -ReviewedDock -DmaRx -ScaledRx [-HighRateRx] -Width 640 -Height 360`（`IDF_TOOLS_PATH=D:/esp/tools` が必要）。トラックMの手順書は `D:/github/airpocket-soundman/hw-ready-2026-11-04/firmware/`（BIN SHA-256 `423b4e8a…4e97`）の使用を前提にしているが、**この PC には該当ディレクトリが存在しない**。使う場合は `claude/track-m-midrate-drive` から再ビルドしてSHAを記録し直す。

### compare_dock_demo.py（J・N・基準線の 20/25MHz 点）

ホスト `tab5-fpga-gpu` の作業ディレクトリで。`<HZ>` は 20000000 または 25000000、`<EDGE>` は `negative`／`positive`。

```
python tools/compare_dock_demo.py --port COM4 --half-ns 25 --setup-ns 25 --guard-ns 2000 --dma-rx-hz <HZ> --dma-scope bulk --readout tile --rx-mode continuous --rx-sample-edge <EDGE> --stream-profile scaled_1024x4 --tx-mode persistent_dma --tx-scope batch --tx-route fixed --tx-hz 5000000 --tx-phase positive --triangle-batch on --empty-tiles on --tile-bins on --scenes 1 2 3 --loads 0 2 --frames 17 --repeats 2 --echo-count 513 --output <OUT>.json
```

## 3. 各試験の手順と合格基準

全試験共通の停止条件：最初の失敗でその系列を止める。再送、自動の周波数ステップ、fallback をしない。`ready_stuck_high`・`response_failed` 以外の予期しないエラー、USB切断、USERCODE不一致が出たら全体を止めて報告。失敗点の結果を成功点に混ぜない。

### 手順1：基準の再現（新ファーム × 85bac224）

FPGA：`baseline_85bac224`。ホスト：トラックMの新BIN。20MHz NEG 合格、20MHz POS 失敗、25MHz NEG ARM失敗、25MHz POS 初フレーム失敗（旧BINでの既知結果）が再現すること。**20MHz NEG が通らなければ新ファームの退行として止める。** 他の3点が旧BINと違えば基準が動くので報告して判断を仰ぐ。

### J：エッジ数カウンタ（`j_edge_counter`、USERCODE 0x4ABF）

1. 書込み、USERCODE=`0x00004ABF` と Status 0x6020 を確認。
2. 2a：20MHz NEG に `--edge-counters` を付けて実行。合格し、`edge_counters.registers` の idx19(excess)=0、idx20(deficit)=0、idx15(reject最大)=0、idx2(異常窓)=0。**どれか非ゼロなら健全点でモニタが異常を出しているので、以降を解釈せず報告。**
3. 2b：20MHz POS、25MHz POS（初フレーム失敗の点）を `--edge-counters` 付きで実行。
4. 2c：ARM で失敗する点（25MHz NEG）は、(1) 20MHz NEG に `--edge-action clear` → (2) 25MHz NEG（失敗を許容、ログに残す）→ (3) 20MHz NEG に `--edge-action read` の順。
5. 判定（観測が揃うまで結論にしない）：失敗点で idx19>0 または idx15>0 → 余分／近接エッジ（仮説B）。idx19=0, idx15=0, idx20=0 で本体CRCのみ失敗 → 仮説A。idx20>0 は単独では原因を断定しない。窓単位のidx4〜14は直後の1回しか意味がなく、集計（idx1,2,15〜20）を使う。`edge_read` 自体も16エッジの窓になる。
6. 追加の制約：J の `CLK_edge_monitor.md` どおり、EDGE=0 のとき 0x4c/0x4d は status 2。

### N：応答位相（`n_phase_t1`〜`t8`）

ホスト：新BIN、FPGAだけ変える（1変数）。各イメージで 25MHz POS → 25MHz NEG を1回ずつ。順は t1 → t2 → … → t8。各書込み後にUSERCODE確認。合格したら同イメージで2回追加（計3回）し、20MHz NEG の対照で退行がないことを確認。ARM失敗・`ready_stuck_high`・`contention`・20MHz対照の退行が出たら、そのtick以上は試さず報告。解釈：合格帯が位相で動く → 仮説A、どのtickでも改善しない → 仮説Bまたは窓以外の原因。**J の結果を先に得ること。**

### B：モデル常駐（`b_model_filtered54`、USERCODE 0x9678）

1. `stop`・`disarm` → 書込み、USERCODE=`0x00009678`、Status 0x6020 を確認。
2. ホストファームを `claude/track-k-model-host` からビルド・書込み（B側の記録では f3fa5e8、BIN `67daf6cd…e05e`、bootloader `acc3e4db…`、partition-table `fd8026bf…`、0x2000/0x8000/0x10000）。この PC にビルド成果物があるかは未確認。
3. 回帰：基準線のコマンド（`--triangle-batch on --empty-tiles on --tile-bins on`）が従来どおり通ること。
4. モデル試験：

```
python tools/compare_dock_demo.py --port COM4 --half-ns 25 --setup-ns 25 --guard-ns 2000 --dma-rx-hz 20000000 --dma-scope bulk --readout tile --rx-mode continuous --rx-sample-edge negative --stream-profile scaled_1024x4 --tx-mode persistent_dma --tx-scope batch --tx-route fixed --tx-hz 5000000 --tx-phase positive --model on --empty-tiles on --scenes 1 --loads 0 1 2 --frames 17 --repeats 2 --echo-count 513 --output <OUT>.json
```

5. 合格：全画面RGB565一致、`wire_accounting.passed`（LOAD 130B／POSE 42B）、`model_skipped_triangles=0`、`model_negotiated`・`model_resident` が真。`MODEL_CAPS` が status 2 なら `MODEL_ENABLE=0` のイメージが載っている。
6. 一致後に `FPGA.state.model_{load,pose,draw}_ms` と従来方式の時間を比較。POSEをタイルごとに再送するため要求バイト数は仕様の見積りより多い。**性能向上は実測まで主張しない。**
7. `--rx-sample-edge negative` は基準線の例コマンドに無く、B側の指定。通らなければ省略版との差として記録。
8. 低速イメージ（3b）を試す場合：`link action=model enabled=true` → `arm` → `step`、`status` で `model_negotiated`・`model_resident`・`model_used` を確認。GPIO接続でDMA・整形返信は無い。

### I：CRC高速化（FPGAは基準線のまま、ホスト `claude/track-i-crc-fast`）

1. 書込み後、`link action=crc_bench iterations=200`（disarmed・idle のとき）。`bitwise_us`、`one_table_us`、`slice8_us`、`crc_equal=true` を記録。P4での実測は未実施。
2. `link action=dma_opt reuse_stream_crc=true`（disarmed・idle）で `codec_ms`（約91ms）が下がるか。対照を挟んで2回測り、差が±1〜2%のノイズを超えるかを見る。
3. 合格：全画素一致、CRC失敗0、`crc_equal=true`、時間が悪化しない。`link_tile_crc_reused` の回数も記録。

### P2：DDR3 `sampleip_map_t4`（USERCODE 0x0233）

ホスト：`claude/track-p-ddr3-clk400-host`（79a28e7）のMEM probeファーム（`tools/build_mem_probe.ps1 -BuildName <新しい名前>`。既存ビルドは上書きされない）。**`sampleip_map` の実機試験で使ったELF SHAは先頭 `1839488d…` しか記録を確認できていない。** 元ファイルは別PCの `D:\esp\ddr3\stage3\`。

1. Dockを電源入れ直し→ t4 を書込み、USERCODE=`0x00000233`、Status 0x6020。
2. 段階1（読取り専用）：`probe_mem_scheduler_diag.py` で `calibrated`・`snapshot_fresh` が真。
3. 段階3：`python tools/mem_stage_runner.py scale --output-dir <dir> --execute --port COMx --expected-elf-sha <ELF>`（4ジョブ約6秒）。`patterns`・`boundaries` も同様に。
4. 合格基準（`sampleip_map` の記録に合わせた比較）：error 0、mismatching_beats 0、128MiB全域で verified_beats 16,777,216。`user_cycles` が `sampleip_map` の 524,489,946 からどれだけ増えるか（t4はビートごとにアイドル1サイクル）を記録。
5. 続けて `fullseeds`（8 seed）、`soak --duration-min 30`、冷起動10回（`docs/DDR3_冷起動_複数seed_soak手順_2026-11-04.md`、P2ブランチ）。結果は「N回中M回、この条件で」と書く。合格を「適合」と書かない。
6. 失敗時は再書込み・再校正をせず、`probe_mem_scheduler_diag.py` を1回記録して止める。

## 4. 失敗時に記録する項目

- 点：FPGA名、FS SHA-256、USERCODE（書込み後の読み値）、Status、ホストBIN SHA-256、`--clock-drive` の有無、日時。
- 条件：周波数、NEG/POS、シーン、負荷、フレーム、Dockの電源入れ直しの有無、室温の目安。
- 失敗の形：失敗種別（ARM／初フレーム／途中）、`failed_dma_dump`、`analyze_dma_capture.py` の出力（CRC位置、欠落byte数）、`request_sequence`、`ready_stuck_high` 等のエラー名。
- J：`edge_counters.registers` の全値（idx1,2,15〜20）、`edge_counters_error`。
- B：`model_*_count`、`wire_accounting`、`MODEL_CAPS` の応答。
- P2：`calibrated`・`snapshot_fresh`、error・phase、`verified_beats`、`mismatching_beats`、`first_bad_byte_address`と期待値・実測値、コマンドFIFOのポインタ、`send_wr`、`refresh_request`（周期的に変わる信号で、1標本は静止状態を示さない）。
- 結果JSONの置き場：ホストの `docs/validation/hw-isolation-2026-11-04/`（トラックMの指定）。

## 5. ブランチ間のマージ可否（キャリア main 53c0239 に対して）

`git merge --no-commit --no-ff origin/claude/<ブランチ>` を hw-queue ワークツリーで実行し、`--abort` で中止（コミットなし）。ブランチ同士は `git merge-tree --write-tree` で確認。

| ブランチ | main単体への統合 | 他ブランチとの衝突 | 備考 |
