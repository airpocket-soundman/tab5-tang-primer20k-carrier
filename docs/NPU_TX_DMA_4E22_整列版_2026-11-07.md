# NPU4E22：任意の受信DATA整列（2026-11-07）

主担当のreview承認後、既存NPU frontendへ既定OFFの`REQUEST_DATA_PIPELINE`を追加した。4E21の既定動作を維持し、専用topだけで整列を有効にする。**この作業ではGowin合成・PnR・書込みを行わない。4E22実機・STAの判定は未実施。**

## 実装と互換性

- `fpga/npu/rtl/npu_ddr_sys.v`：`REQUEST_DATA_PIPELINE=0`を追加。DATAの2段`data_meta/data_capture`と、`request_byte=REQUEST_DATA_PIPELINE?data_capture:data_i`を使う。header、CRC、descriptor、payload、packet RAMの全RX consumerが同じwireを参照する。CLK・DIR同期、RESP、コマンド/CRC規則は維持。
- `npu_ddr_core_8oc.v`：同名parameterを末尾へ追加し、既定0のままendpointへ渡す。旧core/hostのparameter指定を維持する。
- 新`tab5_dock_npu_ddr_8oc_aligned_top.v`だけがparameter1を選ぶ。旧`tab5_dock_npu_ddr_8oc_top.v`は変更しない。
- 新`build_npu_ddr_8oc_aligned_input.tcl`はUSERCODE **4E22**、wire CAPS **4E20**、新規output `fpga/build/npu-ddr-8oc-rx-aligned-v1/`を使う。既存4E21 build、DDR IP/PLL hash、pin制約、SDC方針は変更しない。

raw DATAを約2～3SYS後に読む旧経路では、5MHz正相DMAの次fallでDATAが進んだ後を読める。整列版はCLKと同じ最初のSYSサンプルからDATAを取り、遅延riseに対応するbyteを使う。既存GFXのREQUEST_DATA_PIPELINEと同じ方式である。[原因・候補試験](NPU_TX_DMA_受信データ整列候補_2026-11-07.md)を参照。

## 実際のproduction parameterを使う検証

`run_ddr_rx_phase_sweep.py`はproduction endpointをそのままmodule名だけ変えた2つのコピーへ取り込み、parameter0/1を明示して比較する。候補時の別実装ではなく、実parameter分岐を実行する。

- quick96ケース：PASS。低速0.5/1/2MHzで旧/整列とも全pass、5/8/10MHzで整列全pass。
- 全位相**7326ケース合格**：`fpga/build/npu-rx-production-param-full/result.json`。正相5MHzはparameter0が16/333、parameter1が333/333、8/10/12MHzは0/333対333/333。14/16/20MHzは両者0/333でaliasを確認した。
- full coreは**parameter0/1それぞれ64コマンド合格**。CRC WRITE/READ、IC16+3/OC8全数値、128MiB境界、校正喪失・session/ARM/resetを含む。最終LF sourceの証跡は`fpga/build/npu-rx-production-lf-core{0,1}/`。
- compiled sourceとproductionの8ソースhash一致、build用top/TCLは`fpga/build/npu-rx-4e22-frozen/{checkpoint.json,source_snapshot/}`へ固定した。全phase試験のmodule名を戻したcompiled LF sourceは最終production LF bytesと完全一致する。LF cleanup後もquick96・両core64を再実行した。合成はこの固定版を使う。

試験はSYS27MHz、37位相、DATA delay0/2/5ns、payload16/256/2032B、正相/反転launchを扱う。理想デジタルのCRC/byte/packet RAMの試験で、metastability・電気的setup/hold・ジャンパ配線品質は証明しない。正相12MHzのsim passを実機認定せず、反転launchも未認定とする。27MHz edge detectorは50% dutyでも13.5MHz付近にalias境界があり、14MHz以上では整列だけでは解決できない。

## 4E21の保存と次の実機判定

4E21の復元元は`fpga/build/npu-ddr-8oc-v1/npu_ddr/impl/pnr/npu_ddr.fs`、SHA256 `a9bdae1126f7ffdba349d14293271addbeb4901cee3019bb2315383bf650c05c`。同dirのsource snapshot/qualificationと実機goldenを保持する。既定0の互換性と、旧.fsのbyte一致は異なる事項であり、4E21の再buildを旧保存物へ上書きしない。

4E22は新outputへsnapshotを取り、主担当が配置配線の資源・STAを確認する。4E21自体がCDC/vendor resetのSTA未収束診断版である点を引き継ぎ、包括的なclock除外でtiming合格を装わない。controller IPのDDR row/pin/電気条件も変更しない。

実機は正相GPIO互換→DMA2MHz→5/8/10MHz selftest/連続試験→同じP4 CPU参照との全1000値・phase counter・表示・時間比較の順で確認する。USERCODE4E22とsource/bitstream hashを確認し、失敗時は4E21保存物へ戻す。現在のhost TXDMA8153/2MHz全モデルPASSや、別firmwareの試験を4E22実績へ転用しない。

Linux/MeOS/メモリ研究/ESP-IDFの照合版と未確認事項は原因報告を参照。pin/wire/command変更はなく、正のDATA setupと方向guardを満たすホストが前提。新しい極性自動判定やTX20MHz保証は追加していない。
