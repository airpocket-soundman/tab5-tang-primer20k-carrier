余裕は +0.079ns と薄く、配置配線のばらつきで変わりうる。タイミング適合とは書かない（診断用SDC下の結果で、IP内部の `sys27→user100` 非整数比パスは評価されない）。同じBWエンジンの前回版（t4_bw）は配置が変わっただけで -1.256 → -2.272ns（96本）と振れたため、構造の修正が必要だった。
変更点（BW_ENABLE=0・既存イメージはビット同一のまま）：
1. **IPのreadyループの除去**：IP向けの `cmd_en`／`wr_en` を、IPのreadyフラグと共有の登録済みゲート（BISTとBWエンジンの「次サイクルのゲート」のOR、`!cancel` の次サイクル値を折込み）だけの4入力関数にした（`mem_top` の `BW_SHARED_GATE`、`ifdef BW_GATES`）。従来は2系統の組合せ式のORで3段になっていた。エンジンの内部受理判定（計数用）は従来の式のままで、IP向けenableと全サイクルで一致することを `tb_mem_bw_top` が約206万サイクル検査する。
2. **BWエンジンの登録済みenable**（`mem_bw` の `EN_PIPE`）：`EN_PIPE=1` は `want & !blk` を1サイクル前に登録した `en_*_q` から取り、サイクル挙動は従来と同一。`EN_PIPE=2` は「BIST PIPELINE=4 と同じ構造」（受理直後の1サイクルを止める）で、受理ごとに1サイクルのアイドルが入る。`t4_bw2` は `EN_PIPE=1`（**帯域測定の値に影響しない**）。
3. 次状態の論理から `cancel` を外した（`fail_job` が上書きする分岐のため等価）。64ビットの統計カウンタを16ビット区切り＋登録済みキャリー（`mem_bw_ctr`／`mem_bw_acc`）にした。値はジョブ終了の数サイクル後に確定し、LINK側の読出し（done後）より十分前。
EN_PIPE=2 の期待サイクル（`bw_model.py`）：受理間隔が2サイクル（STEP=2）。理想シムで write_stream は 2N-1、read_stream（L=1）は 2N-1+lat。アイドルは stall に数えない。1ビート/サイクルは出ないので、帯域の上限測定には EN_PIPE=0/1 を使う。
試験：`run_bw_tests.py`（mem_bw 単体を EN_PIPE 0/1/2 × paired/unpaired/rowpad、モデル照合。mem_top統合を BW=1/0、旧IP型スタブ、t4_bw、t4_bw2）と `run_tests.py`（既存回帰）。結果は `fpga/mem/BW_ENGINE.md` 末尾を参照。

## opcode衝突（重要）：BWイメージと MEMV1 は同じ opcode 範囲を別の意味で使う
BWエンジン（`mem_bw_port.v`）の 0x60〜0x6F は、MEMV1（`mem_v1_top`、`claude/memv1-adapter`、main統合済み、仕様 `docs/MEMV1_プロトコル仕様_v1確定案_2026-11-05.md`）の 0x60〜0x67（予約 0x68〜0x6f）と**重なっている**（例：0x62 は MEMV1=RD／BW=CFG_COUNT_LO、0x66 は MEMV1=CRC32／BW=CFG_CTL）。**BWイメージと MEMV1 は別ビットストリームで使い、同一イメージには同居させない。** 識別：BW は QUERY(0x6F,a=0)=0x0150、MEMV1 は CAPS(0x60,a=0)=0x4d31。ホスト（`tab5-fpga-gpu` `claude/mem-bw-host`、`tools/probe_mem_bw.py`）は QUERY署名が0x0150でなければ START前に拒否する。BW実行中にMEMV1のツール（`memv1_xfer.py`）を使わない。
**回避案（提案のみ、RTLは別トラック）**：BWブロックを未使用の **0x70〜0x7F** へ移す（+0x10：CFG 0x70〜0x7A、START 0x7B、CANCEL 0x7C、SNAPSHOT 0x7D、READ 0x7E、QUERY 0x7F。opcode bit7 はタグ付き応答フラグなので 0x7F が上限）。0x5d〜0x7f に既存の使用は無い。`mem_bw_port` の case 定数と `mem_link` の振り分けの書換えだけで、BWとMEMV1を同居できる余地（バス調停は別）も生まれる。ホスト側は `MEM_BW_FIRST` と `probe_mem_bw.py --op-base 0x70` の変更だけで追従する。

## 測定の定義
cycles＝最初のコマンド受理から最後のデータ（書込み受理／読出し受信）までのUSERクロック数（両端含む）、bytes＝(書込みビート＋読出しビート)×16、秒＝cycles/99,562,500、MB/s＝bytes/秒/1e6、効率＝ビート/cycles（1.0＝1.593GB/s）。latency＝lat_sum/lat_samples（サンプリング）。

## 実機手順（親が実施）
1. （t4_bwのSTA改善後）`.fs` をSRAM書込み（フラッシュ不可）。ホストは MEM probe ファームで ARM。
2. ホストファームの汎用アクション `{"cmd":"mem","action":"bw","op":96..111,"arg":u16}`（START は `"execute":true` 必須）と `info.mem_bw_available` は `tab5-fpga-gpu` の `claude/mem-bw-host` で実装（オフラインのみ、実機未検証）。`fpga/host/mem_protocol.h` の BW 定数と応答検査は同ブランチの `bringup/tab5/main/mem_protocol.h` が先行（本リポジトリ側の同期は未実施）。手順の詳細は同ブランチ `docs/mem-bw-host.md`、PC側は同ブランチの `tools/probe_mem_bw.py`（START に execute、`--query-only`、`--op-base` を追加した版）を使う。
3. 先にBISTで 128MiB 全域合格を再確認（既存手順）。
4. `python tools/probe_mem_bw.py --execute --port COM4 --output out.json [--mib 1] [--burst] --bist-after`
5. **合格基準**：全ジョブ done・error=0・非fault、カウンタが計画と一致、チェックサム一致（write/read）、効率≤1.0（超えれば測定無効）、**BWの値（MB/s・効率・遅延・stall比）をJSONと表に記録**（しきい値なし）、続いて `--bist-after` のBIST再合格（exact PASS）。
6. 失敗・cancel後は必ずRECAL（0x5B）。`--burst` の app_burst_number 意味（N+1ビート/コマンド）はサンプルtesterからの推定で未検証。rd_data_end のバースト内挙動も未確認。
