# GFX通信高速化の記録（2026-11-05）

## 実機で確認した範囲

- TX8MHz POS、RX16MHz NEG continuousで640×360全8シーン×3負荷の24画像とFlow次フレーム3負荷がCPU整数参照に一致。
- 同FPGA User8877でTX10MHzへ上げ、同じ24+3画像が一致。最大64triangle/1290byteを1000回、色・深度2,048,000words検証、67.266秒、通信エラー増加0。
- ホスト `tab5-fpga-gpu` の `codex/gpu-speed-next` 67fa672に実機raw結果、SLogic波形、flash/source snapshot、グラフ付きHTMLを保存。ELF b527d3d80e1361e1dbd75a462975152a04a27b2afca3970104c36e9e18e4d16a。
- TX8/10 AB/BA2roundsのFlow高負荷frame1は745.390→715.707ms、3.98%短縮。WireとPolygonの差は小さい。全画像・同wire量・DMA量を確認した。単発画像比較や短いtile stressを全画面120-frame BENCH／長時間soakと混同しない。
- TX16POSは完走1回と複数のtimeout、TX20POSもtimeout。TX16NEGはARM末尾のDMA ID probeを含む段階でresponse不一致。採用しない。GPIOやジャンパ線の上限とは断定しない。

## FRAME_TIMING独立候補

User4264では `FRAME_TIMING_ENABLE=1` を明示。Julia高負荷frame17、TX8/RX16NEG、640×360でOFF505.570→ON472.710ms、逆順ON471.342→OFF505.222ms。画像・計算cycle一致、タイル数240を維持し、cycle問合せを480回からRESET/LO/HIの3回へ削減した。477 exchanges/7632byteを削減。現TX10比較User8877はこの拡張OFFなので、改善率を合算しない。

新headerは `fpga/host/frame_timing.h`、契約と検証は `fpga/gfx/tests/frame_timing_contract.md`。CAPS/RESET/LO/HIの新opcode79..7cは機能OFFなら未対応status2。従来FRACTAL_INFO=021fは変えていない。ホストは明示機能選択とCAPS確認が必要。

## 返信側の候補

- User8877 FAST_FILTER_SYNC=1はSTA4種違反0、実機RX16の画像一致。RX20NEGはARMで失敗、20POSはARM後描画で失敗。
- UserC512登録出力はSTA/限定metadata30pair/sharedclock/RTL/gate検査を通過した保存候補。TX高速化を優先したため実機未投入。
- RAW bypass20/40MHzはSTA違反が残り、実機投入していない。違反を新しいfalse pathで隠していない。
- 詳細は `GPU_RX_返信クロック短縮候補_2026-11-05.md` と `GPU_RX_DATA登録出力候補_2026-11-05.md`。

## 合成後の受信データ経路

8877と94F0のrequest DATA2段RTLは合成後RAM16S4へ変換されていた。RTLモデルをそのまま「16個の同期FFが実装されている」とは説明できない。これを明示DFFに固定した独立候補を準備し、mapped netlist、STA、回帰を通してから同じ条件で実機比較する。RAM変換だけでtimeout原因と確定はしない。

216MHzでCLK/DATAを取り込んで小FIFOからSYS54へ渡す別候補も単体試作中。既存LINKへの統合・STA・実機は未実施。採用済み機能ではない。

## ホスト要求との照合

作業開始時にLinux cfc9a6eのREADME/DEVELOPMENT_GOALS/Device Tree（FPGA通信ドライバは未実装）、MeOS78274b4のREADME/FPGA_CARRIER_REQUIREMENTS/GFX実装、メモリ研究e84b59eの計画、ESP-IDFのProject_B/通信/表示実装を照合した。Linux研究リポジトリでLinux本体の確認を代替していない。

ピン・電源・既存command・frame formatは不変。新FRAME_TIMINGは能力確認して明示選択する追加機能で、既存ホストが使う従来FRACTAL_INFO応答は不変。ESP-IDF側反映は67fa672。Linux/MeOS側の新timer実装・実機試験は未実施で、全OSで新機能を検証済みとはしない。DDRは追加しておらず、LinuxメインRAM増設とは扱わない。

保存点：`fpga/validation/gpu-speed-next-2026-11-05` のFS/STA/HW操作記録とmanifest。User4264/8877は実機試験済み、C512はオフラインのみ。ハードウェアでの比較はFSのSHAとP4 ELFを固定して記録する。

## 追加実機試験：入力FIFO

明示FF候補0454はTX10 Wire/Flow高負荷2画像に合格したが、TX16 Wiretimeoutが再発。cold0454＋新hostb841・fastpackOFFのTX20 polygonもbatch応答CRC/status/sequence不一致となった。FF固定だけで解消したとはしない。

216MHz入力FIFO候補5166（SHA fe5b1d815861bc15056f508e97d09fb78089de390f13153b08f63feee5fcc38f）をSRAMへ書き込み、同じhostb841・fastpackOFF・RX16NEGでTX10/16/20のWire/Flow高負荷各2画像が一致。続くTX20の全8シーン×3負荷frame0、24画像も一致した。TX20最大64triangle/1290byteを1000回、67.844秒、色・深度2,048,000words検証、エラー増加0。

これは全画面デモの長時間運転やジャンパ線の上限確認とは別の試験。Flow次フレーム・polygonバッチ・10対20の速度比較・frame timer統合は別に検証を続ける。5166のoverflowはFPGA物理ARM/resetまたはSRAMreloadで解除する。Tab5ソフトARMでは解除しない。

`request-path-hardware-results.zip` に前候補の不合格を含むrawを保存。5166のメタデータ、DATA/CLK DFFCとGrayの監査は候補docを参照。
