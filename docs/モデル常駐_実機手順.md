## FPGAイメージの作り方（`MODEL_ENABLE=1`、書込みはしない）

### A. この環境で作れた低速イメージ（27MHzコア、機能確認用）

```powershell
$env:PATH="D:/tools/oss-cad-suite/bin;D:/tools/oss-cad-suite/lib;"+$env:PATH
python fpga/builds/dock/build_oss.py trianglemodel --yosys D:/tools/oss-cad-suite/bin/yosys.exe --nextpnr D:/tools/oss-cad-suite/bin/nextpnr-himbaechel.exe --pack D:/tools/oss-cad-suite/bin/gowin_pack.exe
```

トップ `tab5_dock_triangle_model_top`（`tab5_dock_top` に `MODEL_ENABLE` を通した。既定0で既存ビルドは不変）。結果：合成・配置配線・パックまで成功。27MHz目標に合格（`core`の最大周波数 約41MHz）、LUT4 7,031/20,736（33%）、DFF 3,921（25%）、BSRAM 9/46、MULT18X18 23/48。生成した`output.fs` の SHA-256 は `d71aee7f931f44205bbad190c5c8bce6e6e47f3bfbfc3b35fdf0a4226eef594b`（`fpga/validation/model-resident-offline-2026-11-04/trianglemodel27.fs.gz` に保存、manifest付き）。**書込み・USERCODE確認・実機動作は未実施。** これはDMA・整形返信を持たないGPIO接続用で、基準線（0xE368）とは別系統。

### B. 54MHz系（実機の主力）

- OSS版 `triangle54model`（`build_oss.py triangle54model`）は**54MHz目標に不合格**（最大 約43.6MHz）。参考として既存の `triangle54fast`（MODELなし）も同じ環境で不合格（約44.7MHz）。つまり不合格はMODEL追加が原因ではなく、OSS flowが54MHzを満たさない既存の状態で、MODELによる低下は約1MHz。資源はLUT4 7,807（37%）、BSRAM 9。このためOSSの54MHz像は実機に使わない。
- 基準線 `85bac224` と同じ流れのベンダー版：`fpga/builds/dock/build_filtered_model.tcl`（トップ `tab5_dock_triangle54_filtered_model_top`、`MODEL_ENABLE=1`）。Gowin EDA（`gw_sh`）が必要。**この環境にはgw_shが無く未実行。** 実行するPCで `gw_sh fpga/builds/dock/build_filtered_model.tcl` を実行し、タイミング・CDC報告（基準線用のCDC SDCは基準線のネットリスト構造の証明に基づく。MODEL追加で構造が変わっていないか、`filtered-batch-cdc-proof` の検査を再実行して確認）、USERCODE、`.fs`のSHA-256を記録してから書込むこと。

## 実機での試験手順（メイン作業）

1. 書込み前にTab5を`disarm`、ホストを`stop`。基準線のFPGAは電源断で消える（SRAMのみ）。
2. 作ったイメージを `programmer_cli`（`--operation_index 2 --cable-index 1`）で書込み、USERCODEとStatus（0x6020）を確認（既存手順どおり）。イメージのSHA-256とUSERCODEを記録する。
3. Tab5ファームを `claude/track-k-model-host` からビルドして書込み。
4. まずGPIO接続の低速イメージ（A）で：`link action=model enabled=true` → `arm` → `step`。`status`で`model_negotiated`・`model_resident`、`model_used`、`model_*_count`を確認。
5. `tools/compare_dock_demo.py` に `--model on --scenes 1 --loads 0 1 2 --frames 17 --repeats 2`（通信オプションは使うイメージに合わせる。基準線（B）なら基準線の例から `--triangle-batch on --tile-bins on` を除き `--model on` を足す）。合格条件：全画面一致、`wire_accounting.passed`、`model_skipped_triangles=0`。
6. 失敗は再送・従来方式への切替をせず停止して記録する。`MODEL_CAPS`がstatus2なら、イメージが`MODEL_ENABLE=0`である。
7. 一致後に1フレームの時間内訳（`model_load_ms`、`model_pose_ms`、`model_draw_ms`、`tile_read`）を従来方式（`--triangle-batch on`）と比較。POSEをタイルごとに再送するため、仕様の見積もり（約2KB／フレーム）より要求バイト数は多い。性能向上は実測するまで主張しない。

## 未検証・残課題

- 実機でのMODEL_CAPS／LOAD／POSE／DRAW、CPUとの全画素一致、時間。
- ベンダー版54MHzイメージのビルド・タイミング・CDC。OSS版の54MHzは不合格。
- ホストの`app_main.cpp`／`dock_gpu.cpp`のESP-IDFビルド（ESP-IDF v5.5.2が本環境に無く未実施）。
- 深度の向き（上記）。ポーズ再送を減らす設計（インスタンスごとに全タイルへ1回、または複数姿勢の保持）。
