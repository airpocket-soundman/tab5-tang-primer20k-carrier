# sampleip の成功を受けた方針（旧IPの採用、タイミング、段階3以降）（2026-11-04）

実機結果は `fpga/validation/hw-ddr3-variants-2026-11-04/README.md`。**原因が確定したわけではない。** 確認済みの事実と仮説を分けて書く。作成者は実機に触れていない。

## 1. 事実
- `sampleip`（自前ロジック＋サンプルの旧IP、400MHz）：校正完了、先頭1KBのBISTがPASS（verified_beats 128、不一致0、user_cycles 4014）。
- `clk400_notap`／`clk400_asyncsdc`（自前ロジック＋**新ツールで再生成したIP**、400MHz）：校正が完了しない（SDCの違いは無関係）。
- 同じ自前ロジック・同じPLL（属性はサンプルと全項目一致）で、IPだけが違う。従って、**差は新旧のIP生成物にある可能性が高い**。ネットリスト突合で見えた差は、DLL `CODESCAL`／`SCAL_EN`、DQ用IODELAY（5と6）、そして**コマンド／アドレス／制御／CK用のIODELAY（24個、40ステップ）が新IPに無いこと**（差分資料6章）。どれが決定的かは未確認。

## 2. 周波数掃引（新ツールの生成物、`fpga/validation/mem-ip-frequency-sweep-2026-11-04.json`）
| Memory_Clock | tCK | IODELAY総数 | DLL CODESCAL／SCAL_EN | DQ IODELAY |
|---|---|---|---|---|
| 300／324／333／360／380／400 | 3333／3086／3003／2777／2631／2500 | 16 | "111"／"false" | 5 |
| 400＋Debug Parameter | 2500 | 16 | "101"／"false" | 6 |
| 420／450／500 | 5000（不正な値は200MHz既定に戻る） | 16 | "101"／"false" | 0 |

- 新ツールは、300〜400MHzのどこでも、コマンド／CK用のIODELAYを生成しない。サンプルの旧ツール（1.9.8.05）は400MHzで生成した。**周波数・Debug Parameterの設定では再現できない。**（420MHz以上は設定が受理されず既定の200MHz相当に戻る。400が上限のように見えるが、仕様は未確認。）

## 3. 方針

### 3.1 推奨：旧IP（サンプル）を「固定した外部ベンダー部品」として、実験用に採用する
- 理由：新IPでは校正すら通らない。旧IPなら通った（実機）。
- 条件（再現性）：
  - 入手元：公開GitHub `sipeed/TangPrimer-20K-example` commit `e469df4c0c9c41824f405a8515decf24ef1e8e6f`、`DDR-test/LicheeTang20K_DDR_Test/src/ddr3_memory_interface/ddr3_memory_interface.v`（885,814 bytes）。生成ツールは GowinSynthesis V1.9.8.05（ファイル先頭に記載）、IP設定は同ディレクトリの `.ipc`（MEMORY_CLK=400、tREFI 7.8µs 等）。
  - 固定：`fpga/validation/sipeed-ddr-test-reference-2026-11-04.json` に全ファイルのSHA-256（生ダウンロードとLF正規化の両方）。`python fpga/tools/fetch_sipeed_ddr_ip.py` は検証のみ（ネットワークからの取得は `--download`、ユーザー許可が必要）。ビルドは `build/sipeed-ddr-test-e469df4c/` が無い、またはSHAが合わない場合は進めない運用にする。
  - ライセンス：サンプルのディレクトリ全体はBSD 3-Clause（LAKKA）。**中のIPはGowin製の暗号化生成物で、再配布条件は不明**（調査時点でルートのLICENSEは404）。従って**リポジトリにコミットしない**。製品や公開物に入れる前に、Gowinのライセンス／EULAでの扱いを確認する必要がある（未確認）。
  - 制約：暗号化IPのためスケジューラ観測（024f）が出ない。アドレスは14行幅のレイアウト（`sampleip_map` で対応）。ツールは 1.9.11.03 でビルドできている。
- 限界：旧IPが正しいという意味ではなく、**この個体で最初に読み書きが通った構成**という位置づけ。長時間・温度などは未試験。

### 3.2 並行：差を新IP側へ移せるかの調査
- 周波数・Debug Parameterでは移せない（2章）。残る手段：(a) 他のGowin版（1.9.8.05や中間版）のIP生成器で同じ設定を生成し、IODELAYが出る版を探す（取得にはユーザー許可）。(b) Gowinのフォーラム／サポートに、新ツールのDDR3 IPで400MHz向けのコマンド遅延を出す方法を問い合わせる（外部送信になるためユーザー確認が必要）。(c) 旧IPの生成物のうち、アナログ設定（IODELAY／DLL）を変えて効く項目を絞る実験（暗号化IPの加工は行わない）。
- 当面は 3.1 で進め、3.2 は「再生成IPで長期に再現できるか」の確認に使う。

## 4. 段階3以降の準備（`docs/MEM_ペア書込み候補.md` 6章）

### 4.1 FPGA：`sampleip_map`（ビルド済み）
- `sampleip` のBISTアドレスは13行幅の配置で、旧IPの14行幅（`{bank3,row14,col10}`）とずれ、**bank bit0 が行bit13の位置に入る**。先頭1KB（同一行・同一bank）では影響しないが、バンク／行をまたぐ試験と容量試験では誤ったアドレスになる。
- 対応：`mem_bist` にパラメータ `APP_ROW_PAD`（既定0、従来どおり）。1のとき `{bank3, 1'b0, row13, col10}` に配置。シミュレーションで8個の基点を検証（`tb_mem_bist_rowpad.v`、`run_tests.py` に組込み）。既定の回帰（21＋21＋122＋7＋39＋モデル）は不変。
- イメージ：`sampleip_map`（FS `626ada6e…`、USERCODE 0x4C2B、`fpga/validation/mem-variant-sampleip_map-2026-11-04/`）。STA：setup違反あり（最悪 −0.526ns）、hold +0.223、recovery +8.150、removal +0.575。実機未試験。**段階3以降はこのイメージで行う**（`sampleip`は先頭1KBのみ）。

### 4.2 ホスト：`tools/mem_stage_runner.py`（ホスト `claude/track-p-ddr3-clk400-host`、`395d269`）
計画だけを表示するのが既定。`--execute --port COMx --expected-elf-sha <ELF>` で順に実行し、最初の失敗で止まる（再試行・再校正なし）。破壊的。
```
python tools/mem_stage_runner.py patterns   --output-dir <dir>      # 10ジョブ：seed 0／FFFFFFFF／AAAAAAAA／55555555／歩行1（6点）、各1KB
python tools/mem_stage_runner.py boundaries --output-dir <dir>      # 6ジョブ：2KB（列→bank）、16KB（bank→行）、行bit、最終ビート
python tools/mem_stage_runner.py scale      --output-dir <dir>      # 4ジョブ：1KB、1MiB、16MiB、128MiB
```
- パターン：BISTは各アドレスに seed依存のデータと、補数＋バイトマスクの2段を書くので、seed を変えることで00／FF／AA／55相当と歩行ビットを与える。
- 容量alias：全域ジョブ（128MiB）が兼ねる。データがバイトアドレスに依存するため、アドレス別名があれば不一致になる。物理容量は、サンプルが `DDR Size: 1G` と報告した（1Gbit＝128MiB）。小さい範囲を先に（scaleを上から順に）。
- 所要時間の見積り（**64ビートの実測 4014サイクル（2相）からの外挿で未検証**）：約31サイクル／ビート／相 → 128MiB（8,388,608ビート×2相）で約5.2秒（USER 99.5625MHz）。ジョブの60秒期限・ホストの70秒に収まる見込み。
- 試験順序：まず `sampleip_map` で段階1→`patterns`→`boundaries`→`scale`（下から）。失敗したらその場で止め、再書込みや電源入れ直しをせず、直後に `probe_mem_scheduler_diag.py` を1回（ただし`sampleip`系はdeep語0固定）。

## 5. USER 99.56MHz のタイミング対処案（STA setup 最悪 −0.56ns）
`sampleip` の違反の内訳（上位25経路）：
| 起点→終点 | 経路数 | 最悪 | 内容 |
|---|---|---|---|
| `engine/index_*` → `engine/first_actual／first_expected／error_beats の CE` | 15 | −0.560ns | 読出しデータと期待値の128ビット比較（期待値はアドレス＝base＋index×16から組合せで生成）の結果が、そのまま多数のレジスタのクロックイネーブルに入る |
| `control/job_base_*` → `engine/count_latched／seed_latched／busy の CE` | 9 | −0.513ns | 起動要求の受付判定（`valid_range`＝64ビット加算＋比較）が、ジョブ設定ラッチのCEに入る |
| IP内部 `ddr_init_complete_d_3` → `wr_fifo/Almost_Full` D | 1 | −0.515ns | サンプルIP内部。我々の論理では直せない |

対処案（実装すると既存の21＋21シナリオの再検証が要る。**未実施**）：
1. 期待値と比較結果を1段パイプライン化：読出しデータを1サイクル保持し、`mismatch`（不一致フラグ）をレジスタ化してから、誤り計数・first_* の更新に使う。CEの組合せ経路から128ビット比較を外せる。
2. `first_expected／first_actual` の更新は、`mismatch && first_not_captured` を1サイクル前に登録した単一のイネーブルにまとめる（ファンアウト削減）。
3. `valid_range` をmailbox側で事前計算し、START受付時は1ビットのレジスタを使うだけにする（64ビット加算を除去）。または起動を1サイクル遅らせる。
4. それでも足りなければ、期待値生成を1段前倒し（`byte_address` と pattern をレジスタ化）。
5. 補助：配置配線の制約（クロック制約で`user100`のみ厳しくする、`-pr` 実効）、あるいは USER=memory/4 を維持したまま Fmax を稼ぐ以外にない（`clk_out` の分周比は IP固定）。
いずれも「機能保証のためのタイミング適合」を目指す作業で、現状の違反（−0.56ns）でも1KBのBISTは実機で通っている。通った結果は適合の証明にならない（温度・電圧・個体差でどう変わるかは未確認）。
