# DDR3停止：実機結果を受けた次の仮説と、公式サンプルとの差分（2026-11-04）

実機結果は `fpga/validation/hw-ddr3-variants-2026-11-04/`。**原因は特定されていない。** 以下はすべて仮説または比較表で、実機で確認したものは「観測」と明記した箇所だけ。作成者は実機に触れていない。

## 1. 観測（実機、4イメージ共通）
- 校正は完了（calibrated=1）、command_ready／data_ready／scheduler_init_done は真、pre_info_valid は偽。
- 64ビートBISTは4イメージとも error 3 phase 1 verified_beats 0（書込み段階で進行なし）。
- `ddr_cs`固定、リセット保持の除去、校正後待ちの延長（256→60000）は、結果を変えなかった。
- 失敗後の受理数・FIFOポインタ・send_wrは今回未記録（前回との同一性は未確認）。

## 2. 公式サンプルとの差分（今回変えていないものを含む）
サンプル：Sipeed `TangPrimer-20K-example` commit `e469df4c`、`DDR-test/LicheeTang20K_DDR_Test/src/`（`ddr3_syn_top.v`、`tester.v`、`ddr3.sdc`、`gowin_rpll.v`、`ddr3_memory_interface.ipc`）を公開GitHubから読んだ（本リポジトリには未保存）。

|---|---|---|---|
| IP版 | v3.0、`app_burst_number[5:0]`あり（8バースト時7、1バースト時0）、`burst`も接続 | v5.9、`burst`のみ（1'b1） | 未 |
| メモリクロック | 400MHz（PLL 27×59/4=398.25MHz、IDIV3／FBDIV58／ODIV2）、user約99.56MHz | 324MHz、user 81MHz | 未（(a)） |

## 3. 優先順位つきの次の仮説（効果の予測ではなく、安く切り分けられる順）

**P0（イメージを作らない、実機でも安全）：失敗後の内部状態の記録。** 今回の段階2は、受理コマンド数・コマンドFIFO・send_wr・refresh_request・pre_info_valid を残していない。各イメージで、段階2の失敗直後に（再書込み・電源入れ直し・再校正をせず）`probe_mem_scheduler_diag.py` を1回実行して保存する。さらに、静止状態で`refresh_request`を数回読み、周期的に変わる信号か、立ちっぱなしかを区別する（base・refwaitは真、rst・cs0は偽という差の解釈に必要）。

**P1（RTLのみ、IP再生成不要、ホスト変更不要）：`pace`（サンプルと同じコマンドペース）。** サンプルは256サイクルに1回しか発行しない。本リポジトリは連続発行でFIFOを満杯にする。コントローラが、満杯／連続発行に弱い（または最初のコマンド受理後に何かの準備が要る）可能性の切り分けになる。`prepare_variant.py pace`で生成済み（コマンドとデータをともに`pace_counter==0`のときだけ出す）。シミュレーションは、間隔を8サイクルに縮めた複製で既存21シナリオが通ることまで確認。256サイクルの値そのものは、ベンチのタイムアウト（60サイクル）が短いため未シミュレーション。**未ビルド**。

**P2（IP再生成、ホスト変更不要、STA不安は小）：IPのタイミング値をサンプルに揃える（324MHzのまま）。** tREFI 7.8µs、tRFC 160ns、tRAS等。ただしサンプルの部品が2Gbitと推定されており（`MEM_ペア書込み候補.md`）、本部品（資料上1Gbit H5TQ1G63EFR）の保守的な値と食い違う。部品の実値は未確認なので、サンプルの値が安全とは限らない。IPを作り直すと`MemDDR3.vo`のSHA-256とネット名が変わり、`prepare_deep_taps.py`の024f観測が成立しない可能性がある。

**P3（IP再生成、ホスト変更あり、STAが通らない恐れ）：(a) 400MHz。** 4.の設計を参照。USER約99.56MHzはFmax 81.7MHzの現行設計では通らない可能性が高い（要ビルド確認）。

**P4（実機側の確認、安い）：物理個体。** 校正完了までは通っているため、電源・VREF／VTTが極端に外れている可能性は下がるが、「校正が通る程度に動作」と「連続書込みの動作」は別なので除外できない。VDDQ、VREF（約0.75V）、VTT、CK／リセット波形の測定は未実施。測れれば優先度を上げる。UD1の刻印と容量（1/2Gbit）の確認も含む。

**P5（IP版の違い）：サンプルのIP v3.0（`app_burst_number`）と本リポジトリのv5.9（`burst`）の挙動差。** v5.9の入力仕様（IPUG281）を再確認し、`burst`以外に必要な入力がないかを確認する。Education 1.9.11.03 で v3.0 を選べるかは未確認。

仮説の並び順は、P0→P1→P4を並行→P2→P3→P5。P0とP4はイメージ不要。

## 4. (a) 400MHz に必要な変更（設計。未実施）

FPGA側：
1. `generate_ip.tcl`：`Memory_Clock 400`（ほかのタイミング値の扱いはP2と合わせて決める）。
2. `mem_pll.v`：IDIV=3／FBDIV=58／ODIV=2（27×59/4=398.25MHz、VCO 796.5MHz）。
3. `mem_bist.sdc` と `prepare_guarded.py` が生成するSDC：メモリクロック398.25MHz、user=÷4（約99.56MHz）に更新。`create_generated_clock`の係数は`-multiply_by 59 -divide_by 4`相当（要確認）。
4. `mem_mailbox.v`：SYSQUERY 4／5の戻り値（324／81）、スナップショットword30（81）。398.25は整数に収まらないため、**表記を決める必要がある**（案：memory=398、user=100とし、実周波数は下記の表で解釈）。`mem_bist.v`の100msタイムアウト（8,100,000サイクル）と60s期限（4,860,000,000）はサイクル数なので、時間が約0.8倍になる点を記録に残す。
5. `prepare_deep_taps.py`／`prepare_guarded.py`：VOのSHA固定とネット名（`n219_4`等）の再突合。

ホスト側（`tab5-fpga-gpu`、別ブランチで）：
1. `bringup/tab5/main/mem_protocol.h`：`case 4: value==324; case 5: value==81;` を、許可するペア（324,81）と（398,100）の表に変える。
2. `tools/probe_mem_bist.py`：snapshot word30 の81固定（33行）と`values[:6] != [..., 324, 81]`（139行）を同じ表に。`user_cycles`→時間の換算（現在`user_clock_hz`=81MHz固定）は、ペアに対応する実周波数（81MHz／99.5625MHz）を使う。
3. `tools/test_mem_wire.cpp`、`tools/test_probe_mem_bist.py` のペア表の試験を追加。
4. ホストMEM probeファームの再ビルド（`tools/build_mem_probe.ps1 -BuildName <新名>`）。他のファーム（GFX等）には影響しない。
ホストの変更は、(a)のイメージがビルド・STA確認できてからにする。
