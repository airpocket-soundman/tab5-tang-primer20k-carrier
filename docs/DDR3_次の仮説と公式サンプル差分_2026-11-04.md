# DDR3停止：実機結果を受けた次の仮説と、公式サンプルとの差分（2026-11-04）

実機結果は `fpga/validation/hw-ddr3-variants-2026-11-04/`。**原因は特定されていない。** 以下はすべて仮説または比較表で、実機で確認したものは「観測」と明記した箇所だけ。作成者は実機に触れていない。

## 1. 観測（実機、4イメージ共通）
- 校正は完了（calibrated=1）、command_ready／data_ready／scheduler_init_done は真、pre_info_valid は偽。
- 64ビートBISTは4イメージとも error 3 phase 1 verified_beats 0（書込み段階で進行なし）。
- `ddr_cs`固定、リセット保持の除去、校正後待ちの延長（256→60000）は、結果を変えなかった。
- 失敗後の受理数・FIFOポインタ・send_wrは今回未記録（前回との同一性は未確認）。

## 3. 優先順位つきの次の仮説（効果の予測ではなく、安く切り分けられる順）

**P0（イメージを作らない、実機でも安全）：失敗後の内部状態の記録。** 今回の段階2は、受理コマンド数・コマンドFIFO・send_wr・refresh_request・pre_info_valid を残していない。各イメージで、段階2の失敗直後に（再書込み・電源入れ直し・再校正をせず）`probe_mem_scheduler_diag.py` を1回実行して保存する。さらに、静止状態で`refresh_request`を数回読み、周期的に変わる信号か、立ちっぱなしかを区別する（base・refwaitは真、rst・cs0は偽という差の解釈に必要）。

**P1（RTLのみ、IP再生成不要、ホスト変更不要）：`pace`（サンプルと同じコマンドペース）。** サンプルは256サイクルに1回しか発行しない。本リポジトリは連続発行でFIFOを満杯にする。コントローラが、満杯／連続発行に弱い（または最初のコマンド受理後に何かの準備が要る）可能性の切り分けになる。`prepare_variant.py pace`で生成済み（コマンドとデータをともに`pace_counter==0`のときだけ出す）。シミュレーションは、間隔を8サイクルに縮めた複製で既存21シナリオが通ることまで確認。256サイクルの値そのものは、ベンチのタイムアウト（60サイクル）が短いため未シミュレーション。**ビルド済み**（FS `61711981…`、USERCODE 0xB8F0、全STA違反0、setup余裕+0.023ns）。実機未試験。

**P2（IP再生成、ホスト変更不要、STA不安は小）：IPのタイミング値をサンプルに揃える（324MHzのまま）。** tREFI 7.8µs、tRFC 160ns、tRAS等。ただしサンプルの部品が2Gbitと推定されており（`MEM_ペア書込み候補.md`）、本部品（資料上1Gbit H5TQ1G63EFR）の保守的な値と食い違う。部品の実値は未確認なので、サンプルの値が安全とは限らない。IPを作り直すと`MemDDR3.vo`のSHA-256とネット名が変わり、`prepare_deep_taps.py`の024f観測が成立しない可能性がある。

**P3（IP再生成、ホスト変更あり、STAが通らない恐れ）：(a) 400MHz。** 4.の設計を参照。USER約99.56MHzはFmax 81.7MHzの現行設計では通らない可能性が高い（要ビルド確認）。

**P4（実機側の確認、安い）：物理個体。** 校正完了までは通っているため、電源・VREF／VTTが極端に外れている可能性は下がるが、「校正が通る程度に動作」と「連続書込みの動作」は別なので除外できない。VDDQ、VREF（約0.75V）、VTT、CK／リセット波形の測定は未実施。測れれば優先度を上げる。UD1の刻印と容量（1/2Gbit）の確認も含む。

**P5（IP版の違い）：サンプルのIP v3.0（`app_burst_number`）と本リポジトリのv5.9（`burst`）の挙動差。** v5.9の入力仕様（IPUG281）を再確認し、`burst`以外に必要な入力がないかを確認する。Education 1.9.11.03 で v3.0 を選べるかは未確認。

仮説の並び順は、P0→P1→P4を並行→P2→P3→P5。P0とP4はイメージ不要。

## 6. pace の実機結果と「5件でfull」の分析（追記）

観測（`hw-ddr3-variants-2026-11-04/pace-after-fail.json`）：`pace`（256サイクルに1回の発行）でも、段階2は error 3 phase 1。失敗直後は受理コマンド5、受理データ5、コマンドFIFO write pointer 5・read pointer 0・full、`send_wr` 0、`pre_info_valid` 偽。コントローラがコマンドを取り出さない点は、ペース制御でも変わらなかった。

### 6.1 なぜ5件でfullか（仮説。実機・シミュレーションでは未確認）
- コマンドFIFOのポインタは3bit（深さ8）。VO（`MemDDR3.vo`）には `gw_cmd0/full_r`・`full_rr`（fullの2段遅延）があり、次の書込みポインタ更新に使われている。
- 前回の連続発行（ペア発行、`be42c604`）は7件、今回の間隔発行は5件。**差の2は、fullの2段遅延と一致する**：連続発行ではfull（実効的な満杯しきい値）がready低下に反映される前の2サイクルでさらに2件入る。間隔発行ではその余分が入らず、しきい値の5件で止まる。
- この解釈なら、FIFOの実効しきい値は「5件」で、読出し側が1件も取り出さないため、どの発行方法でも満杯で止まる。**受理数の違いは、停止の原因ではなく、停止後に溜まる量の違い**と考える。
- 確認方法（未実施）：`MemDDR3.vo`＋ベンダー`prim_sim.v`で、読出しを止めたままコマンドを連続／間隔で入れ、受理数5／7が再現するか見る。
- 根拠の限界：しきい値5の算出式は、VOを読んだだけでは特定していない（LUT配線のみ確認）。

### 6.2 追加の観測
- `refresh_request` は固定の信号ではない（同じイメージで真→偽）。前回の「立ちっぱなし」を原因の手掛かりとして使わない。
- `pre_info_valid` は、全6イメージ・静止状態・失敗後のいずれでも偽。

### 6.3 再順位付け（6イメージが同じ失敗になった後）
RTL側の変更（`ddr_cs`、リセット保持、校正後待ち、発行ペース）はすべて無効。これらはユーザーロジック側の差であり、ベンダーのコントローラ（暗号化IP）の内部状態は同じまま。残るのは「ベンダーIPが見ているもの」：クロック・リセット・IP設定・物理。

1. **P0'（イメージ不要）**：失敗後の内部状態に加え、静止状態の`refresh_request`・`pre_info_valid`を数回読む（周期性、時間変化の確認）。今回の記録で`refresh_request`は動くと分かったので、`pre_info_valid`が永続的に偽かどうかを確かめる。
2. **P4（電気測定）**：6イメージが同一なので、物理個体／電源の優先度を上げる。VDDQ・VREF（約0.75V）・VTT・CK波形・RESET#。校正は通るが、書込みコマンドを消化しない点は、読出し／書込みのタイミング余裕や信号品質の問題でも説明可能（未検証）。
3. **`readfirst`（RTLのみ、新規）**：BISTを読出しから始める。読出しコマンドをスケジューラが処理すれば（`verified_beats`>0、error 6の不一致は想定内）、問題は書込み系に絞られる。読出しも止まれば、スケジューラ全体の停止。`prepare_variant.py readfirst`で生成済み。**ビルド済み**（FS `6249526e…a820`、USERCODE 0x9A6C、全STA違反0、setup +0.063ns）。実機未試験。
4. **`norst`（RTLのみ、新規）**：IPの`ddr_rst`を未接続にする（サンプルと同じ）。`prepare_variant.py norst`で生成済み。**ビルド済み**（FS `d2986c03…2ece`、USERCODE 0xADA0、全STA違反0、setup +0.593ns）。実機未試験。
5. **P2（IPタイミング値をサンプルに揃える）**／**P5（IP v3.0対応）**／**P3（400MHz）**：ここまでと同じ。P3は現行のUSER Fmax(81.7MHz)では約99.56MHzが通らない恐れがある。

## 7. norst・readfirst の実機結果と再順位付け（追記）

観測：
- `norst`（IPの`ddr_rst`未接続）：段階2は error 3 phase 1 verified 0。他と同じ失敗（失敗後の再取得は未取得）。
- `readfirst`（読出しから開始）：error 4 phase 2 verified 0。失敗後、受理コマンド1（読出し）・書込みデータ0、コマンドFIFO write pointer 1・read pointer 0・**full 偽**・`send_wr` 0・`issue_read` 偽・`pre_info_valid` 偽。**読出し1件すら取り出されない。**
- これで8イメージ（base、refwait、rst、cs0、pace、norst、readfirst＋前回のbe42c604実機）で、スケジューラは読出し／書込み／FIFO満杯の有無／発行ペースにかかわらずコマンドを1件も取り出していない。`pre_info_valid` は全標本で偽。

解釈（仮説。実機・シミュレーションでは未確認）：
- 停止は、コマンドの種類や量ではなく、**スケジューラが何かの前提条件を満たしていない**ことで起きている。`scheduler_init_done` は真だが、`pre_info_valid` が一度も真にならない。
- 前提条件を満たさない理由の候補は、ユーザーロジックの外にある：ベンダーIPが見るクロック・リセット、IP設定とDRAM部品の不一致、物理（電源・信号品質）。校正完了（calibrated）が通る点は、DRAMがある程度は応答していることと整合するが、読み書きの余裕は別。
- ユーザーロジック側の変更（`ddr_cs`、リセット、待ち、ペース、`ddr_rst`、読出し先行）はすべて結果を変えなかったので、これ以上のRTL変種は効果が薄い。

再順位付け：
1. **公式サンプルをそのまま、この個体で動かす（最重要の切り分け）。** サンプルの`tester`はUARTに結果を出す。サンプルが通れば、物理個体は少なくともその条件で動作し、本リポジトリのIP設定／統合が原因側に絞られる。通らなければ個体／基板が疑わしい。サンプルの合成は前回、Education 1.9.11.03で成功している（`ddr-education-qualification-2026-11-04.json`）。必要なもの：サンプルのソース一式の取得（公開GitHub commit `e469df4c`、暗号化IPを含む。取得は許可が必要）、UART出力を読む配線（サンプルは`uart_txp`）、JTAG書込み（メインセッション）。**未実施。**
2. **電気測定（VDDQ、VREF、VTT、CK、RESET#）。** 8イメージ同一の失敗なので優先度を上げる。
3. **IPのタイミング値・版をサンプルに揃える（P2、P5）。** サンプルとの差分表（2章）の未変更項目が候補。ただし、1で通れば、それらのうちどれが効くかを絞るのに使う。
4. **400MHz（P3）。** 現行設計のUSER Fmaxの問題あり。
5. 失敗後の内部状態の追加観測：ベンダーFSMの状態（`bank_state`＝262144は静止・失敗後で同一）の意味づけには、ネットリスト解析かシミュレーションが要る。
