# MEMV1 高速転送設計（PARLIO＋DMA 化）（2026-11-05）

ホストからの DDR3 READ／WRITE（`MEMV1`、opcode 0x60〜0x67）を、GPIO リンクから PARLIO＋DMA に載せる設計。**オフラインの設計文書で、実機（COM4、Dock、書込み、JTAG）には触れていない。** 本文の数値は「実測」「仕様」「見積もり（推測）」を区別して書く。実機で確認していないことは「未検証」と明記する。

- 基点：キャリア main `c4dfa19`、ホスト `tab5-fpga-gpu` main `443fd16`（作業開始時）。
- 参照した資料：`docs/MEMV1_プロトコル仕様_v1確定案_2026-11-05.md`、`fpga/validation/hw-memv1-2026-11-05/README.md`（実機合格）、`fpga/validation/hw-membw-2026-11-05/README.md`（DDR3 帯域）、`docs/引継ぎ_2026-11-04.md`、`docs/引継ぎ_2026-11-05.md`、`docs/Dock返信クロック整形実験.md`、`fpga/link/rtl/{reply_clock_filter,link_reply_raw,link_bringup_filtered}.v`、`fpga/mem/rtl/memv1_sys.v`、ホスト `docs/memv1-host.md`、`docs/dma-optimization-track-e.md`、`docs/crc-fast-track-i.md`、`docs/continuous-rx-highrate.md`、`main/{dock_gpu,dock_dma_rx,dock_dma_tx,mem_xferx}.*`。
- Linux／MeOS／メモリ研究側（`tab5-linux-fpga`、`tab5-meos-fpga`、`esp32p4-linux-fpga-memory`）は**本作業では再調査していない**（版は統合方針メモ1章のまま）。本設計はホスト ESP-IDF 側の経路であり、他ホストへの適合は M1 合格後に確認する（未確認）。

## 1. 現状の律速要因

### 1.1 実測・仕様から得られる値
| 項目 | 値 | 根拠 |
|---|---|---|
| 4KiB の片道（GPIO リンク） | 約 1.3 s | 実測（ホスト `docs/memv1-host.md`、引継ぎ 2026-11-05） |
| `xferx` の既定タイミング | 約 300 µs／バイト | ホスト `docs/memv1-host.md`（既定タイミング） |
| MEMV1 FPGA 側 PHY の想定上限 | 500 kHz 以下（SYS 27MHz 同期） | 本リポジトリの仕様前提（実測した上限ではない） |
| DDR3 内部帯域 | 約 512 MB/s（seq）、142〜200 MB/s（行ミス系） | 実測 `hw-membw-2026-11-05`（1MiB、1回ずつ） |
| DDR3 内の 4KiB の所要 | 約 8 µs（4096 B ÷ 512 MB/s） | 上の値からの計算 |
| 応答の期限 | READY 待ち 100 ms（ホスト）、FPGA TIMEOUT 約 81 ms | 仕様・ホスト資料 |
| チャンク | 最大 256 ビート＝4 KiB | 仕様 2章 |

### 1.2 フレームのバイト数（仕様 2章から）
8 ビット幅なので、1 クロックで 1 バイト。ペイロード P＝16×ビート数（4KiB で 4096 B）。

| 命令 | 要求 | 応答 |
|---|---|---|
| RD | 8＋8＋2 ＝ 18 B | 8＋P＋2 ＝ 4106 B |
| WR | 8＋8＋P＋2 ＝ 4114 B | 8 B |
| CRC32（256 ビート） | 18 B | 8＋4＋2 ＝ 14 B |

タグ付き（`op|0x80`）は応答に 8 B（`c3`×8）が付く。以降の計算では省く（4106→4114 B で 0.2%）。

### 1.3 時間の式
1 チャンク（P＝4096）の所要時間を次のように置く。

`T_RD = O_h + B_req/f_tx + T_ddr + B_resp/f_rx`、`T_WR = O_h + B_req/f_tx + T_ddr + B_resp/f_rx`

- `f_tx`、`f_rx`：ホストの PARLIO クロック（バイト／秒＝Hz。8 ビット幅）。
- `O_h`：1 回の要求あたりのホスト固定費（DMA 開始・DIR 切替・READY 待ち・キャッシュ・CRC16／CRC32・コピー）。
- `T_ddr`：FPGA 側の実行（CDC バンドル往復＋DDR3 の 4KiB）。見積もり 約 20 µs（DDR3 約 8 µs＋CDC 数 µs〜十数 µs。**推測**、実機で未測定）。100 ms の期限に対して無視できる。

### 1.4 現状の分解（GPIO リンク）
- 実効：4224 B ÷ 1.3 s ＝ 約 3.25 kB/s ＝ **約 308 µs／バイト**（約 3.2 kHz 相当のバイトレート）。
- FPGA 側 PHY の想定上限 500 kHz ＝ 2 µs／バイトであり、現状は上限の約 **1/154**。**律速は FPGA 側ではなく、ホストの GPIO ビットバンギング**（バイトあたり約 300 µs。`pause()` で `half_us`／`setup_us`／`guard_us` を待つ方式）。したがって、**FPGA だけ（A 案）を高速化しても、ホストが GPIO のままなら速くならない**。これが選択肢比較の出発点（本設計の主要な結論の 1 つ）。
- フレーム形式のオーバーヘッド：RD は応答 4106 B のうち 10 B（0.24%）、WR は要求 4114 B のうち 18 B（0.44%）。**バイトのオーバーヘッドは無視できる**。
- CRC16＋CRC32：FPGA 側は受信中にバイト単位で計算（`memv1_sys.v` の `crc`、`memv1_crc32b`）、READY 待ちの前に終わるので律速ではない。ホスト側は、CRC16 が slice-by-8 で 4106 B あたり約 70 µs（トラック I の見積もり：5〜7 サイクル／バイト、P4 360MHz。**P4 では未測定**）、WR の CRC32（zlib）が 4096 B あたり数十 µs（**推測**）。いずれも GPIO の 1.3 s に対しては無視でき、20 MHz では 1 チャンクの 10〜20% に相当し得る（`O_h` に含める）。
- READY 待ち：FPGA 実行は約 20 µs（推測）だが、ホストは 100 ms 期限まで待つ作りで、ポーリング／割込みの粒度が `O_h` に入る。**実機の READY 待ち時間は未測定**。

### 1.5 `O_h` の見積もり（推測）
GPU の実測（引継ぎ 2026-11-04、ポリゴン高負荷 568 ms、240 タイル）：TX 約 77 ms、RX 約 121 ms、ターンアラウンド約 11 ms から、1 タイルあたり TX 約 0.32 ms、RX 約 0.50 ms、ターンアラウンド約 0.05 ms。RX 2066 B の配線時間は 20MHz で 0.10 ms なので、固定費は約 0.4 ms 前後が RX 側にあると読める。TX は 8 B コマンドの周辺で固定費が主。合計して **`O_h` ≈ 0.4〜0.9 ms／要求**（下限は Track E の有界スピン・ゼロコピー、Track I の CRC 再利用を適用した場合）。MEMV1 の経路では未測定で、**M0 で最初に測る**（測定項目は 3.4章）。

## 2. 高速化の選択肢

### 2.1 前提（実機で確認済みの GPU 側の能力）
- 連続 RX（PARLIO＋DMA、1024×4 リング、`scaled_1024x4`）：1/2/5/8/10/16/20 MHz が実機合格（FPGA 85bac224、640×360 の全画素一致）。25MHz 以上は未合格（位相で合否が変わる）。
- persistent TX DMA：0.5/1/2/5 MHz（TX の合格点。5MHz が上限）。
- FPGA 85bac224：`reply_clock_filter`（216MHz サンプラ、2 サンプル一致でクロック整形、最小立上り間隔 5 tick＝約 23.15 ns）で整形したクロックで、`link_reply_raw` が応答をバスクロック領域で直接シリアライズ。リクエストは生 CLK を SYS54 の 3 段同期で受ける。5MHz／20MHz 連続 RX で合格。
- MEMV1 の FPGA 側（`memv1_sys.v`）：SYS 27MHz。バスクロックを 3FF（`clk_sync`）で受けて立上りを検出し（`rise`）、データを `rise` の周期で取り込み、応答は `tx_index`（SYS 領域のカウンタ）から組合せで `data_o` を作る。GPU の高速応答経路は**使っていない**。

### 2.2 PHY の時間余裕（推測。実機未測定）
`clk_sync` 2 段後の `rise` で `tx_index` が進むので、バスクロックの立上りから応答データが更新されるまで 2〜3 SYS サイクル（27MHz で 74〜111 ns）＋BSRAM 読出し等の 1〜2 サイクル（37〜74 ns）。**合計 約 110〜185 ns（推測）**。ホストが次の立上りで採るまでの余裕は：

| f_rx | 周期 | 判定（推測） |
|---|---|---|
| 0.5 MHz | 2000 ns | 余裕あり（仕様上の想定上限） |
| 1 MHz | 1000 ns | 余裕あり |
| 2 MHz | 500 ns | 余裕あり（応答 110〜185 ns） |
| 5 MHz | 200 ns | **ぎりぎり、または不足**（配線往復・Tco・ホストのセットアップを引くと負の可能性） |
| 20 MHz | 50 ns | **不可**（応答が間に合わない） |

要求側（`rise` 後に `data_i` を取り込み）は、ホスト TX の 5MHz（周期 200 ns、データは次の立上りまで保持される前提）では取り込みが 74〜111 ns 後で、保持が前提なら成立し得るが、`data_i` は非同期のまま取り込まれており（GPU 側の SYS54 の 3 段同期も同じ流儀）、余裕は小さい（推測）。GPU の応答側を高速化した理由（応答の遅れ）が、そのまま MEMV1 の応答側に当てはまる。

### 2.3 選択肢の定義
- **A**：MEMV1 の LINK を GPU の高速応答経路に載せ替える（FPGA の RTL 変更）。ホストは GPIO のまま。
- **B**：ホスト側だけ、GPIO から PARLIO＋DMA へ（既存ドライバ再利用）。FPGA は現行 `mem_v1_top`（FS `8dd98907…`）のまま。
- **C**：A と B の両方。

### 2.6 結論（比較から）
1. **B が先**。A 単独では効果ゼロ（GPIO が 99% を占める）。B は RTL 無変更で 0.5〜2MHz なら確実性が高く、効果が最も大きい（約 150〜500 倍）。
2. A は、B で PHY の限界が実機で確認された後に、**応答側だけ**（RD と CRC32 の応答）を最小の RTL で高速化する（要求側は SYS の 3FF 受けのまま）。MEMV1 の応答は GPU の TILE 応答と形が近い（ヘッダ＋ペイロード＋バインド CRC16）ので、`link_reply_raw` の構造をそのまま転用しやすい（設計上の見込みで、実装は未着手）。
3. WR は TX の 5MHz が壁なので、A の効果は RD に限られる。

## 3. 第1段の詳細設計（B ＋ 必要なら応答のみ A）とマイルストーン

### 3.1 方針
1. **M0（前提）**：現行 FPGA（`8dd98907…`）のまま、ホストを PARLIO＋DMA 化して 0.5→1→2 MHz。PHY の実際の上限を測る。RTL は動かさない。
2. **M1：5MHz で 4KiB 往復が全バイト一致**。まず現行 FPGA で 5MHz を試す（B のみ）。応答が不成立なら、応答のみ A（3.3章）を入れて再試験。
3. **M2：20MHz（RD のみ。WR は TX 5MHz のまま）**。A の応答経路が前提（現行 PHY では不可、2.2章）。
4. 各段は 1 変数ずつ。自動再送・自動 fallback はしない（既存方針、MEMV1 仕様 2章）。

### 3.2 ホスト側の設計（B）
- TX：`dock_dma_tx` の persistent DMA（実機合格 0.5/1/2/5MHz）で要求（WR は 4114 B、RD は 18 B）を送る。`mem_xferx.hpp` の要求検査（先頭が CRC 有効な MEMV1 ヘッダ）と、DIR 切替順（バスを入力に戻してから DIR）を維持。1 要求＝1 トランザクション。
- RX：応答長は要求から既知（RD＝8＋16×ビート＋2、WR＝8、CRC32＝14）。**有限 RX（長さ指定）**で受ける案を第一とする（連続 RX のパーサは TILE 専用で、4106 B のボディは 1024×4 リングで 1 要求を保持する前提が未確認）。連続 RX（20MHz 実績）で長い応答を扱う案は M2 の検討項目（`link_stream_feed` の MEMV1 応答対応）。有限 RX の最大長と 5〜20MHz での合格は**未確認**（有限 RX は 5MHz の合格が中心）。
- READY：GPU は `ready` を待つ（DIR=1 後）。MEMV1 の WR/RD は実行に約 20 µs（推測）なので、有界スピン（Track E の `spin_us`、有限 RX のみ）が効く可能性がある。期限は 100 ms のまま（FPGA TIMEOUT 約 81 ms）。
- CRC：応答の CRC16 は 1 回だけ検証（Track I の slice-by-8、重複計算の省略）。WR の CRC32 は送信前に計算（ROM の CRC があれば利用。**P4 での所要は未測定**）。RD は CRC16 トレーラで足りる。内容の最終確認は FPGA 側の CRC32 命令を使う（3.6章）。
- キャッシュ：RX の DMA 宛先は内部 SRAM のリングとし、`esp_cache_msync`（C2M／M2C）の要否と、宛先 PSRAM への memcpy（PSRAM 書込みは約 28 MB/s とみられる＝4KiB で約 146 µs。Track I の**推測**）が、20MHz の 205 µs に対して無視できない大きさになることを計測する。PSRAM へ直接 DMA できるか、ダブルバッファでオーバーラップできるかを検討（未検証）。
- 周波数：`f_tx`＝0.5/1/2/5MHz、`f_rx`＝1/2/5/8/10/16/20MHz（合格済みの点のみ。自動増加なし）。位相（NEG／POS）は GPU の基準線の設定を引き継ぐ。

### 3.3 FPGA 側の設計（応答のみ高速化。M1 で必要になった場合、M2 で必須）
`memv1_sys.v` の要求側（SYS27 の 3FF、状態機械、CRC、ステージング、`memv1_bridge` の CDC）は**そのまま**にし、成功時の応答（RD、CRC32、およびヘッダのみの応答）の**出力段だけ**を GPU の経路へ置き換える。
- 216MHz の `reply_clock_filter`（`clean_clk`、最小立上り間隔 5 tick）を、バス CLK（生）から作る。`fault`（応答中の過早な立上り）で OE／READY を遮断する既存の振る舞いを踏襲。
- 応答シリアライザ（`link_reply_raw` 相当）を `clean_clk`（≤ 54MHz 相当の保守的なクロック指定）で駆動：ヘッダ 8 B（`5a status seq 02 r0 r1 crc`、タグ付きなら `c3`×8 前置）→ペイロード（読出しバッファの 128 ビット幅から 1 バイトずつ）→CRC16 トレーラ（`link_reply_raw` の `crc_byte` と同じバインド CRC）。CRC32 命令の応答は 14 B。
- 読出しバッファ（BSRAM 4KiB）の読出しポートを `clean_clk` 領域にする。書込みは USER（99.56MHz）で、`done_t` の 2 段同期後に SYS が `offer` を立てるまで読出し側は動かさない（ホールド付きバンドル。`link_reply_raw` の「offer から done まで metadata は不変」という方式を流用）。`r_addr` の先読み（128 ビット＝16 バイトごとに 1 回）で、各語が次のホストサンプルまでに確定することを RTL 位相試験（`run_fastreply_frequency.py` 相当）で確認する。
- 追加クロック：216MHz の rPLL。MEM イメージは既に memory 398.25／USER 99.56MHz で PLL を使うので、**GW2A-18 に空き rPLL があるか（＋DDR3 IP との共存）は未確認**。無い場合の代替は、サンプラを memory クロック（398.25MHz）に置き、`cooldown`／2 サンプル条件の tick 数を再パラメータ化して再検証（非自明で、リスク大）。
- 合成・STA：SDC に `conditioned_reply`（54MHz 保守）と sampler216 を明示（matched-no-objects 不許可）。公式 Education（Gowin）で配置配線し、sampler216 の被覆（71 path 前後）を確認。ホールド付きバンドルの `set_max_delay` による裏付けは現状無いので、**この段で併せて追加**する（blanket 非同期グループへの依存を減らす）。
- 資源：現状 Logic 6861／20736、BSRAM 16／46、Register 5721／16173。シリアライザと整形で数百 LUT 規模（**見積もり**）。再合成後に STA 違反 0 を確認し、記録する。
- RTL 試験：Icarus で、`tb_mem_v1_core` の既存 208 チェックが不変で通ること、新たに（a）`reply_clock_filter` 経由の RD 256 ビート応答が全周波数条件（5/8/10/16/20MHz × 位相 × 遅延）でバイト一致、（b）ステータス≠0 の 8 B 応答、（c）CANCEL／STALE／リセット時の OE 遮断、（d）停止 CLK、を追加する。**未実施**。

### 3.5 検証の設計（オフラインで先にやること）
1. ホスト側の PC 試験：`mem_xferx.hpp` のモック（要求エンコード、`memv1_model.py` との一致）を PARLIO 経路のフレーム長（18/4114/4106/8/14 B）に拡張。DIR 切替と DMA の順序は ESP の実機でしか確認できないので、ロジックだけネイティブ試験。
2. FPGA 側（A を入れる場合）：Icarus の位相試験（5〜20MHz × 3 SYS 位相 × 2 サンプル位相 × 片道遅延 0/2/5 ns × Tco 0/2 ns）を、RD 256 ビート応答に対して 85bac224 と同じ手法（`run_fastreply_frequency.py`）で回す。

### 3.6 重みのロードと運用（4章に続く）
上記の設計では、1 回の RD／WR は 4KiB で、**CRC32 命令も 256 ビート（4KiB）ごと**（仕様 2章：ビート数 1〜256）。全体の内容確認に CRC32 命令を使うと、65MiB で 16640 回の往復（18 B 要求＋14 B 応答、各 `O_h` ≈ 0.3〜0.5 ms）が追加になり、約 5〜9 s（推測）かかる。これを避ける v1.1 の提案：CRC32（および将来の COPY／FILL）は、ステージングを使わない**長い範囲（例 1 MiB 以上、32bit のビート数）**を受け付ける（FPGA 内で DDR3 を 512 MB/s で読み、65MiB でも約 0.13 s＋）。仕様変更（opcode の追加、RTL）で、**本設計では未着手の提案**。

## 4. DDR3 帯域とリンクの差、YOLO 重みのロード

### 4.1 帯域の差（数式）
- DDR3：`B_ddr` ≈ 512 MB/s（seq、実測。理論 1593 MB/s の 32%）。
- リンク：`B_link` ≤ `f × 1 B`（8 ビット）＝ 20 MB/s（RD、20MHz）、5 MB/s（WR、TX 5MHz）。プロトコル込みの有効値は 2.1〜6.5 MB/s（2.4章）。
- 比：512／20 ＝ **25.6 倍**、512／5 ＝ **102 倍**、有効 3.6〜6.5 MB/s に対して約 80〜140 倍。DDR3 の 4KiB は約 8 µs、リンクの 4KiB は 5MHz で 821 µs（102 倍）、20MHz で 205 µs（25.6 倍）。**転送はリンクで律速**で、DDR3 の帯域はホスト経由では使い切れない。DDR3 帯域が効くのは FPGA 内部（NPU／GFX が DDR3 を直接読む構成）だけ。

### 4.2 YOLO 重み 65MiB のロード時間
N ＝ 65 MiB ＝ 68,157,440 B。チャンク数 ＝ N ÷ 4096 ＝ 16,640。

| 条件 | 式 | 時間 |
|---|---|---|
| 配線のみ、20 MB/s | N ÷ 20e6 | 3.41 s |
| 配線のみ、5 MB/s | N ÷ 5e6 | 13.63 s |
| プロトコル込み WR 5MHz（O_h＝0.4／0.9 ms） | 16640 × (0.845 + O_h) ms | 20.7〜29.0 s |
| WR 2MHz | 16640 × (2.08 + O_h) ms | 41〜50 s |
| WR 1MHz | 16640 × (4.13 + O_h) ms | 75〜84 s |
| WR 0.5MHz | 16640 × (8.25 + O_h) ms | 144〜152 s |
| 現状 GPIO | 16640 × 1.3 s | 約 21,600 s（約 6.0 時間） |
| （参考）DDR3 内部のみ | N ÷ 512e6 | 0.133 s |

ユーザの見積もり「3〜13 秒」は**配線のみの下限**で、プロトコル込み（4KiB ごとの往復）では 20〜29 秒（WR 5MHz）が現実的な見込みで、**固定費 `O_h` の削減**（有界スピン、CRC 再利用、ゼロコピー）が効く。`O_h` を 1/4 にできれば（0.1〜0.2 ms）約 16〜17 s。さらにチャンクを大きくする（BSRAM の拡大、または WR のステージング方式の見直し）ほど配線のみの値に近づく（仕様変更・未着手）。

### 4.3 提案：重みの書込みを一度きりにする運用
重みは**推論中に書換えない**ので、リンクで運ぶのは次の 3 つに限る：(a) 重みの初回書込み（電源投入後 1 回）、(b) 入力画像（例：640×640×3 の INT8＝1.23 MB、20MB/s で約 61 ms、5MB/s で約 245 ms。NPU 側の実装・入出力の形は**未確認**）、(c) 出力。
1. **常駐 FPGA イメージの固定**：MEM（MEMV1）イメージを再書込みしない（FPGA の再構成で DDR3 の内容が失われる可能性が高い。保持の有無は**未検証**）。
2. **世代による再ロード判定**：STATUS の世代（語1）が、書込み時から変わっていなければ DDR3 の内容は有効とみなし、再書込みしない。世代が変わった（リセット、校正喪失、USER リセット）場合のみ再ロード。ただし電源断・DDR3 リフレッシュ停止後の内容保持は**未検証**で、安全側は「世代が変われば再ロード」。
3. **WR は一度きりで検証付き**：WR は CRC16（リンク）＋CRC32（内容）が両方通らないと DDR3 に書かない（仕様）。さらに、ロード後に FPGA 側 CRC32 を領域単位で取り、ホストが持つ期待値（重みファイルの CRC32 を連鎖計算）と一致を確認。長い範囲の CRC32（3.6章の提案）があれば約 0.13 s、現行の 4KiB 単位なら 5〜9 s（推測）。
4. **ブート時バックグラウンド**：初回ロード（約 20〜30 s）は起動時に開始し、UI／他の初期化と並行（有界・分割・取消し可能。MEMV1 の CANCEL を利用）。推論開始は CRC 確認後。
5. **圧縮・量子化**：INT8 から INT4 などで 65MiB を半減できれば時間も半減（精度は別途、YOLO トラックで検証）。
6. **再ロードの回避**：ホストの待機（ディープスリープ等）中に FPGA 側の電源を維持する構成は、キャリアの電源設計の範囲（未検討）。

## 5. 未確認事項（推測・未検証の一覧）
- PHY（`memv1_sys.v`）の実際の上限周波数：0.5MHz 以下は仕様前提。1/2/5MHz の成否、応答の間に合い方（2.2章の 110〜185 ns は**推測**）は未測定。
- `O_h`（0.4〜0.9 ms）は GPU の TILE のフェーズ時間からの逆算で、MEMV1 では未測定。READY の実待ち時間、DDR3 の 4KiB の FPGA 内所要（約 20 µs）も未測定。
- 有限 RX の最大長と 5〜20MHz での長い応答（4106 B）、連続 RX で MEMV1 応答を扱う場合のパーサ拡張の要否。persistent TX で 4114 B を 1 回で出せるか。
- キャッシュ整合（内部 SRAM リング＋memcpy／PSRAM 直接 DMA）と PSRAM 書込み速度（約 28 MB/s は Track I の推測）。
- 216MHz の rPLL が MEM イメージ（旧 IP、memory 398.25／USER 99.56MHz）と共存できるか、STA（診断用 SDC の blanket 非同期グループの下で余裕 0.023〜0.057 ns）、ホールド付きバンドルの `set_max_delay` による裏付け。
- DDR3 の再構成後の内容保持、冷起動の繰返し、温度、長時間。DDR3 帯域は 1MiB・1 回ずつの測定。
- TX を 5MHz より上げられるか（WR の上限）。20MHz は RX（RD）のみの実績。25MHz 以上は GPU 側で位相依存の失敗が残る。
- 長範囲 CRC32、チャンク拡大（4KiB 超）は仕様変更で、未設計。
- 他ホスト（Linux／MeOS／メモリ研究）への適合は本作業では再確認していない。本設計はホスト ESP-IDF 側の経路。
- 旧 IP（Sipeed サンプル）の再配布条件は未確認（既存の課題）。
