# NPU見積もり 追加考察（2026-11-04）

[NPU実現性見積もり](NPU実現性見積もり_2026-11-04.md) の議論の記録。**すべて見積もり・推測で、実機・合成での実証は無い。** 実機には触れていない。

## 1. 出力は画像でなくてよい
- 戻す量は画像ではなくモデル出力 1x29x420＝12,180要素（INT8なら12,180B、型は未確認）。入力61,440Bの約2割。
- 出力の意味（BB座標・キーポイントの並び）は未確認。後処理（NMS等）をFPGAで行えばBB座標のみ（数十〜数百B）にできるが、NMS実装の手間が増える。後処理をP4に任せるなら12KBを戻す。
- 通信時間への効果は小さい（10MB/sで7.4ms→約6.2ms）。入力を減らす余地の方が大きい（グレースケール化で約1/3、カメラからFPGAへ直接入力は現構成で未検討）。後処理の担当が決まったら本文の通信込み表を更新する。

## 2. ボトルネックは通信ではなく計算
- P4最良実測（約4.45GMAC/s、13.7ms）に勝つには、通信ゼロでも稼働率0.6で54MHz約137レーンが要り、DSP上限96を超える。通信は差を広げるだけ。
- P4が遅い場面（37〜91ms）では通信4〜15msは1〜4割程度で、計算器が足りれば通信込みでも勝つ余地がある。
- 通信が主因になるのは実効5MB/s以下、または小モデルを1枚ずつ処理する場合。実効5〜20MB/sは仮定で、NPU用通信は未実測。

## 3. FPGAが不利な理由
- 並列数：乗算専用回路は最大96（9x9、未検証）。P4は128bitレジスタで1命令にINT8を16個（推論、一次資料未確認）。
- クロック：実績27〜54MHz、P4は360MHz前後（約7〜13倍差）。
- 理論上限96x54MHz≒5.2GMAC/s、稼働率0.6で約3.1GMAC/s（稼働率は仮定）。再量子化は乗算1個の約8倍で共有が必要。

## 4. フラクタルがCPUより速い理由（推測を含む）
記録（引継ぎ資料3章、少数反復、CPU側のSIMD利用は未確認）：Mandelbrot負荷0 595ms対471ms、負荷2 2036ms対616ms。
- 画素ごとに独立で入力が少ない。専用固定小数点回路で命令読出しがない。
- 反復が増えてもFPGAはほぼ吸収（負荷0→2でCPU 3.4倍、FPGA 1.3倍）。負荷0のFPGAは転送・ホスト処理が下限と推測（内訳未測定）。
- ポリゴンは逆（CPU 143ms、FPGA 404ms）。やり取りが多く、CPUの計算が元々速い。
- NPUはデータ移動（重み・特徴マップ）が大きい点で異なる。

## 5. DDR3の位置づけ
- 重み約0.6MBはBSRAM（約103KiB）に入らず、DDR3が動かなければNPUは成立しない（必要条件）。
- DDR3が動いても、P4最良ケースには勝てない。勝てるのはP4が遅い条件のみ。
- 勝敗を決める量：特徴マップのDDR3往復量（20MBは仮定、100MB仮定なら96レーン54MHzでも約126msで帯域律速）、DDR3持続帯域（0.8GB/sは仮定）、稼働率（0.3〜0.6は仮定）。
- 実機なしでできる次の作業：モデルの層表から特徴マップ量を算出し、不確実性を減らす。

## 6. OS・GUI負荷下での価値（CPU占有の観点）
- Linux／MeOS＋GUIでP4に余裕がない場合、評価軸は「速さ」から「P4のCPU時間をどれだけ空けられるか」に変わる。非同期に投げれば推論中もGUIが止まらない。メモリ帯域（PSRAM）競合でP4が遅くなるなら、FPGA化の利点になりうる（競合時のP4実測は無い）。
- ただし通信自体にCPUを使う。ポリゴンは1フレーム568msのうちホスト処理が約223ms（CRC約5.4MB/s が最大）。Linux／MeOSで同じDMA経路が使えるかは未確認。
- ホスト側にFPGA演算の利用経路は無い（引継ぎ資料11章）。
- 最小デモの評価項目に「CPU占有率」「GUI負荷下のP4推論時間」を加える（案）。

## 7. FPGAが速い可能性のある他の処理（仮説、未検証）
条件：転送1バイトあたりの計算量が多い／要素が独立／整数・固定小数点・ビット演算中心／状態がBSRAMに収まる。

| 候補 | 理由 | 懸念 |
|---|---|---|
| SDFレイマーチング等の手続き描画 | フラクタルと同構造 | 反復数のばらつきでレーン待ち |
| 粒子の全組合せ計算（N体、群れ、衝突） | 計算N²、入出力N | 粒子数がBSRAMで制限 |
| セルオートマトン、反応拡散、格子流体 | 状態をFPGA内に置ける | 格子サイズがBSRAM制限 |
| ビット演算（ハミング距離、popcount、パターン照合） | LUT向き、DSP不要 | 用途未定 |
| 二値・三値NN（XNOR＋popcount） | 乗算不要でLUTに多数レーンを並べられる | 精度低下、既存WholeBody25は使えない。NPUの代替案 |
| モンテカルロ、乱数 | 出力小、LFSRが軽い | 用途限定 |

向かないもの：小さなフィルタ（3x3 Sobel等）やFFTの小規模なもの。計算量が転送量に比例し、転送律速でCPUが速いと見る。
引継ぎ資料の残り5シーン（Wire・Particles・Galaxy・Fire・Flow、トラックL）は粒子・セル型と重なる。
優先案：(1) 粒子全組合せ、(2) SDFレイマーチング（`fpga/gfx/compute` の題材）、(3) 二値NNを `estimate_throughput.py` に加えた試算（実機不要）。
