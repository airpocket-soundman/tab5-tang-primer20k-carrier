## 公式実例から確認できるライフサイクル

| 段階 | 公式ソースの根拠 | MEMV1へ採る意味 |
|---|---|---|
| new | 単純例143行、advanced例169行 | ジョブ／セッション開始にユニットを確保する |
| enable | 単純例144行、advanced例170行 | 設定・バッファ・ピンの準備後に有効化する |
| callback登録 | 単純例146〜150行、公式テスト105〜109行 | 完了をISR側で通知し、待機タスクを起床できる |
| transmitを反復 | 単純例201〜206行、公式テスト119〜122行 | 同じハンドルで複数回送信する。要求ごとのnew/deleteは不要 |
| wait／通知待ち | 単純例206行、公式テスト120・122行 | DMA完了前にバッファを再利用しない。期限付きwaitを使う |
| disable | 公式テスト124行、ドライバ608行以降 | 終了・中断の状態遷移を完了させる |
| delete | 公式テスト125行、ドライバ396〜417行 | セッション終了時に資源を返す。enabled状態のdeleteは禁止 |

これは意味上の順序で、公式例ではcallback登録をenableの後に行っている。送信開始前に登録を完了する点が重要。公式テスト59〜64行はenabledのままdeleteするとINVALID_STATEになることも確認している。

公式テスト68〜75行の完了callbackは、ISR用通知で待機タスクを起床するだけの小さい処理で、119〜122行では同じTXハンドルとバッファを使い2回送信する。これは本プロジェクトの「常駐consumerがDMA完了を待ち、producerは空きslotを待つ」方式の直接の参考になる。公開ヘッダ113〜126行はcallbackのISR文脈と、cache-safe設定時のIRAM条件を示す。callback内で描画、JSON生成、確保／解放、通常タスク用の待機APIを呼ぶ構成にはしない。

## payload・キュー・二重バッファの寿命

ドライバ656行以降のtransmitはpayloadのアドレスとビット長をトランザクション記述子へ保持し、DMAのリンクへ渡す。送信APIが返っただけではDMA消費完了を意味しない。これはソースから導く所有権上の条件であり、元payload全体を内部へ複製してくれる前提でfree／書換えをしてはいけない。送信中のslotはconsumer/DMA所有、完了確認後にだけproducerへ戻す。キューに入った各payloadも同じ寿命条件を満たす必要がある。

`trans_queue_depth`は単純例32、公式テスト8。これはドライバのトランザクション容量で、アプリの安全なpayload slot数とは別である。queue_nonblockingは「満杯時に送信登録を待たない」指定であり、DMA本体の完了や、ドライバ内部すべての処理の非待機・期限を保証しない。ドライバ420〜433行のwait_all_doneは完了キューを受信して記述子をREADYへ戻す。完了callbackの通知だけでドライバ内の記述子回収まで済んだと仮定せず、この回収手順も維持する。

advanced例67行には静的な2面の送信フレームバッファがあり、88〜94行のbuffer-switch callbackで表示側へ切替完了を知らせ、121〜123行で送信対象と次のバッファを切り替える。生成しながら別バッファをDMA送信する参考にはなる。ただし同例は表示用loop transmissionであり、MEMV1のREADY/DIRによる有限要求・応答へloop動作をそのまま持ち込まない。

payloadのアラインメント、内部／外部メモリ、キャッシュ整合は実ターゲットの条件に従う。公式ドライバ685〜695行もアラインメント確認とCPU→DMA向けのキャッシュ同期を行う。バッファを保持することと、必要なcache syncまで省略することは別である。プロジェクトの16bit DMAに必要な8bit→16bitのpackも、ユニット再利用だけでは消えない。

## 公式サンプルでもbusy待ちは区別する

単純例196行は、yieldしない描画・反復ループでタスクWDTになり得ることをコメントしている。advanced例220〜227行は次の処理時刻までvTaskDelayする。公式例にwhileループがあることだけを根拠に、低CPU用途へCPUを占有するループを転用しない。

さらに、公式ドライバ560〜562行には、GDMA開始後にTX FIFO readyを確認する短いspinループがある。後続のwait_all_doneにtimeoutを付けても、この前段ループ自体へ同じtimeoutが及ぶわけではない。したがって「送信登録API全体が必ず所定時間以内に戻る」「ISR通知だけでCPU負荷ゼロ」とは主張しない。ジョブのCPU runtimeと各phase時間を別々に測る必要がある。

## 本プロジェクトへ適用する範囲

標準的な再利用の基本形は「一度確保→複数transmit／完了待ち→終了時disable/delete」。本プロジェクトでは、これにTX/RXのバス所有権と共有APBリセットを加える。リセット後に、保持したTXのクロック・データ幅・位相・DMA設定・GPIOの経路等を正しく復元しなければ、ハンドルが残っていてもハードウェア設定が残るとは限らない。ここは公式のTX単独例からの推論だけで済ませず、プロジェクト側の実装・読戻し・実機比較が必要な差分である。

比較は同一FW・FPGA・TX/RXクロック・位相・preamble・guard・scratch領域で行う。従来full reset、payload/RX unit再利用、TX保持＋full APB後復元を混ぜず、同じ要求列・slot数で、全header／payload CRC・seq・WR後の全byte読戻しを確認する。全jobのARM、準備、転送、検証、drain、終了処理を含む時間とCPU task runtimeを記録し、alloc/free、unit create/delete、APB/Core/FIFO reset、実callback数が狙いどおり変化したことも保存する。失敗時は最初で止め、再試行でPASSへ置換しない。

ここまでの公式ソース調査と、以下に追記するプロジェクト実機試験は別の証拠である。初稿時の未認定状態から、下記の限定条件を実測で確認した。

### 8MHz物理波形と10MHzの限界

`slogic-8mhz-caps/`は収録終了0、CAPS全9要求・全9応答PASS。`clock-and-response-summary.json`と同ディレクトリの原`capture.sr`、`short-caps-analysis.json`、保存P4応答バイナリを保持した。100MS/s・50,000,000保存サンプルで、TX/RXの周期は12／13サンプル、8MHzの公称125nsと整合する。TX histogramの大きい値は要求後の間隔で、周期列へ補正していない。

全9要求は先頭zeroを含む9バイト全体が共通のphysical rising−20ns／−10nsで期待値と一致。全9物理応答も共通の固定位相で8バイトCRC一致し、保存P4応答全9件が期待値と一致した。バイトごとの位相選択やedge削除はない。10ns分解能のデジタル閾値観測であり、アナログsetup/holdやP4内部取得位相を直接確定したものではない。

`pilot-restore-10mhz-wrrd10.json`は最初の要求でdevice_status、完了0・FAIL。保持した応答`5a01410200009f24`はstatus1 FORMAT。10MHzは不合格で、8MHzの結果から10MHz以上へ認定を拡張しない。自動再試行や位相の自動fallbackで失敗を隠していない。

### 計測範囲とCPU／ISRの解釈

全job帯域はpayload総数÷job_wall_usの十進MB/s。ARMによるリンク確立、要求生成、DMA準備、転送、返信検証、producer drain、session終了、DISARMを含む。PC側USB API往復・100ms status polling・LCD描画は含まない。したがって4KiB単一要求の往復帯域、PCまでのend-to-end帯域、DDR内部帯域とは別の値である。

WR/RDのpayload総数は書込みと読戻しの合計で、8.192MB／1000組。これは半二重リンクの両方向合計実効帯域であり、同じ数値の書込み単独速度と読取り単独速度を同時達成した意味ではない。個別方向の同期transfer合計は別計時で、producer準備と返信検証を含まない。

runtimeはESP_TIMERを使うFreeRTOSのproducer／consumer実行時間差分。両taskはcore1に固定され、consumer優先度5／producer4。示す百分率はこの2taskの合計時間÷job wallであり、全chip CPU率ではない。ISRが割り込まれたtaskへ時間を計上される場合もあり、純粋なアプリ命令時間だけではない。snapshotの粒度・取得コストと終了tailの差がある。queue待機とDMA待機は壁時間で重なり得るので、単純合算してwallから差し引きCPUを推定しない。

完了callback数は実登録されたTX/RX完了callbackの呼出し数で、20000要求runでは各20000。全物理IRQ数と同一ではなく、descriptor完了等のdriver counterとは区別する。`module_phase_wall_us`と`transaction_wall_us`にも内包・重複する区間があり、全項目を足してCPUや総時間と解釈しない。遅い要求の除外はしていない。
