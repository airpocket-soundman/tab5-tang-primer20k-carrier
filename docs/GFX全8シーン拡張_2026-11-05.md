# GFX全8シーン拡張（実験仕様）

対象はGPU LABのWire/Polygon/Mandelbrot/Julia/Particles/Galaxy/Fire/Flow。
既存GFX命令とピン・電源・LINK CRC/sequence/方向転換規則は維持する。
`ALL_SCENES_ENABLE=1` の独立GFX候補だけで有効。MEM/NPUとの同時搭載は行わない。
既存ビットストリームが新しい能力を持つとは扱わない。

## 計算の配置

| シーン | CPU | FPGA |
|---|---|---|
| Wire | 既存の回転・投影 | Bresenham線描画 |
| Polygon | 既存の回転・投影 | 三角形・深度 |
| Mandelbrot/Julia | 視野パラメータ | 反復計算・色付け |
| Particles | 粒子位置 | 3×3矩形描画 |
| Galaxy | 軌道・粒子位置 | RGB加算合成 |
| Fire | frame/load指定 | 整数ノイズ・補間・熱量・色付け |
| Flow | 既存の粒子物理更新 | 線/点・残像減衰・障害物描画 |

Flow残像はホストRAMに保持し、前タイルをFPGAへ再投入→減衰→描画→読み戻す。
CPUが描いた画像をGPU結果とする方式ではない。障害物は表示だけに合成し残像へ入れない。
非連続frameはframe0から状態を再生する。速度・メモリ消費は統合実機で計測する。
Fireのinteger_g0は新しい固定小数点規則で、legacy_floatの炎とは画素一致を主張しない。
CPU/GPUの整数版同士で一致を判定する。従来CPU浮動小数点版は保存する。

## コマンド

opcodeはGFX種別の名前空間。`fpga/host/raster2d_protocol.h` を参照。
通常要求/応答は従来の8byteで、上位tag bitは従来の同期prefix規則のまま。

- 60 CAPS = 011f（v1、線/矩形/加算/タイル投入/減衰）。
- 61..6a: x0,y0,x1,y1,color565,addRG,addB,kind,reserved0,reserved1。
  座標はtile-local signed16の整数。kindはPixel0/Line1/Rect2/Add3。
  Lineは元の両端点と誤差を維持し、書込みだけを32×32へclipする。
  Rectは両端inclusive。ADDはRGB565を8bitへfloor展開、RGB888を飽和加算して565へ戻す。
- 6b DRAW、6d UPLOAD_RESET、6c UPLOAD_WORD、6f FADE（各565成分×29/32）。
  全1024word投入が完了するまでtileは未初期化扱い。超過・部分投入後の描画は拒否。
- 6e DRAW_BATCH、5f UPLOAD_BATCH: header count1..64/format1、10word×count、CRC trailer。
  全payload CRC検証後だけ実行する。DRAWは10setter+draw、UPLOADは10word投入+NOPを繰り返す。
  5e NOPは引数0のみ。1024word投入は640+380wordの2batchと4scalarを使う。
- 70 FIRE_CAPS = 0101。71..77: originX/Y,width/height,frameLo/Hi,load。
  78 DRAW。640×360/320×180/160×96、load0..2だけ許可。

未対応命令status2、引数不正status3、初期化/設定不足status5。
reset/abortは新しい設定・途中UPLOADとRAMの有効性を取り消す。
能力不足・CRC不一致・途中停止を自動再試行やCPU画像で置換しない。

## 検証順序

4. 既知のTX8/RX5で全8×3負荷の画素比較。
5. 全8×3負荷のRUN SUITE、停止/再ARM、表示・JSON/CSV保存。

## 実機確認と選択した保存点

選択はv5、UserCode `94F0`、status `6020`。
FS SHA256は `7660c5be31dd99c7522ddb46cfcaf31ffd088314ec0e8d5aef0f10cc90969b9f`。
公式ProgrammerのSRAM書込み、独立したUserCode読出し・status読出しは全てexit0。
FPGAの不揮発flash書込みは行っていない。

同じ640×360のホストファーム（ELF `8793810267d96bf41a3536d5c9806f46e9e2ef648de70a124622b5d3e1c0614d`）、
ジャンパ8bit、TX8MHz POS／RX5MHz NEG、継続RX・scaled1024×4・bulk/tile・常駐TX・fixed routeで、
全8シーン×3負荷のframe0、計24比較の全画素一致に合格した。
さらにFlowのframe1を3負荷で比較し、FPGAで作った前frame残像の保持・再投入・減衰を含め全画素一致した。
640×360の計27比較で6,220,800画素を照合した結果である。
CPU画像への置換や通信失敗後の自動再試行を成功扱いにしていない。

この保存点の報告は画像比較であり、640×360の全48項目（CPU/GPU×8シーン×3負荷）の
24ウォームアップ＋120動的フレーム完走とは別。
160×96の全RUN SUITEは別のホスト実機試験でCPU/FPGA各24ケース×120フレームを完走した。
三角形一括化ONの検証専用条件で、640×360の全負荷120フレーム測定と同一視しない。
最終640デモELF `1bef2d9252a573061621528190bf8bdc1fc3abaaf5af16ed6c65c0b93805e0ca` の
起動時TX8/RX5・batch ON設定、全8LIGHT画像一致と停止/DISARMも確認した。
計算・通信・表示時間や速度比較はホスト側の
[全8シーンレポート](https://github.com/airpocket-soundman/tab5-fpga-gpu/blob/codex/gpu-matched-tx-bench/docs/validation/all-scenes-2026-11-05/report.html)
とその生記録を参照する。全シーンでCPUより高速という結果ではない。

| v2 route0 | setup1、hold0、最小setup −0.040ns | 書込せず。同じ経路の違反が残った |
| v3 / 8E20 | setup0、hold0 | reply_activeの2FF同期で内部タイミングを解消。TX8の最初の合法な2D batchでstatus3。未合格 |

### CLKとDATAの対応付け

以前はCLKを3段SYS登録し、`clk_sync[1] & ~clk_sync[2]` を消費する時点で
パッケージからの `data_i` を直接読んでいた。54MHzでは物理CLKの観測から約37～55.6ns遅れた
DATA取得になり、TX8MHz POSの次のfallまで62.5nsというモデルでは最小約7nsしか残らない。
v4のREGISTER_INPUTはこの時点で採ったbyteを次のSYS周期へ渡す変更で、採取時刻自体は変えない。

v5は `REQUEST_DATA_PIPELINE=1` によりDATAもCLKと並列に2段SYS登録し、遅れて検出したriseに
対応する元のDATA sampleをreq・CRC・batch・bad-request診断で共通に使う。
既定0は従来動作を維持する。新topだけでREQUEST_DATA_PIPELINE、REGISTER_INPUT、
REPLY_ACTIVE_PIPELINEを全て1にしている。DIR/OE/READYの即時解除と受信画像の送信回路は変更していない。

合成用デジタルモデルでは、8MHzでDATAをfallから次fallまでだけ保持し、CLKだけをDATAに対して
0/10/20ns遅らせた。portable/filtered、5初期位相、最大1290byte batchを含む計180packetでv5方式は全一致。
従来方式は遅延0で一致し、10ns・20nsのモデルでは不一致を再現した。
**10ns・20nsは試験で与えた仮定で、ジャンパ線やFPGA端子で測ったskewではない。**
このモデルと実機での改善は採取時刻整合の効果を支持するが、アナログ波形・setup/hold余裕や
ジャンパ接続の周波数上限を確定した証拠ではない。MEMの既存TX8試験はNEG＋preamble1であり、
GFXのPOSと同じ条件とは扱っていない。

### 資源・STA・保存物

v5のGowin1.9.11.03 Education配置配線結果はLogic6759/20736、register2952/16173、
BSRAM5/46、DSP16.5/24。全27,611 paths、9,087 endpointsを解析しsetup違反0／hold違反0。
GFXはDDR3を使わず、Flowの残像保持先はホストRAMである。

SDCは既存のmetadata bundled-data第一段だけの30対を維持し、対象対が元のqualified SDCと
完全一致することを保存ツールで確認した。今回の機能追加・ACTIVE/DATA pipeline用に新しい
false path、multicycle、clock groupを追加していない。外部ジャンパ信号のアナログ整合はこのSTAの範囲外。

保存先は [fpga/validation/all-scenes-2026-11-05](../fpga/validation/all-scenes-2026-11-05/manifest.json)。
v1～v5のSTA/PnR/ログ、v3～v5のFS、選択v5の自作output VO、実機operationログ、
640画像照合の生JSON、RTL/clockモデルのPASSログ、現時点のRTL/CST/SDC/ヘッダーsource ZIPとSHA256を保存する。
Gowin primitive library、暗号化netlist/IP、DDR controller IP、実行ファイルは収録しない。

source ZIPはアーカイブ取得時点の内容で、build前に取得した原本hashではない。
選択projectの入力ファイル一覧、現在の各入力hash、TCL/実行ツールhash、合成netlist hash、FS hashを
区別して記録している。特にv1～v4は版ごとの元source snapshotが無く、現在のZIPで過去版を
再現できるとは主張しない。合成VGはhashだけを残し、選択v5の自作output VOで生成結果を識別する。

## ロジックアナライザーの現行配線

SLogic16U3の全信号は [完全特定の保存記録](../fpga/validation/probe-map-complete-2026-11-05/manifest.json)
を正とする。CLK=D7、DIR=D6、READY=D4、DATA0～7=D15～D8。
100MS/s・50,000,000 samplesを欠落なく取得し、既知のtagged CAPS9往復で全byteとCRCを照合した。
内訳は有効selector0～7と、引数不正status3を期待するselector8の1往復である。
CLIのexit0だけで完了扱いにせず、実100,000,000 packed bytesとchunk連続性を再確認している。
以前の暫定配線推定は履歴として保持し、この完全特定結果とは区別する。

## NNベンチとの分離

2026-11-05のNN追加の相談に対し、既存の用途別構成方針に沿って、NN用は別のNPUビットストリームを推奨する。
現GFXは汎用命令プロセッサではなく、共通2D、三角形/深度、共通フラクタル、Fireを組み合わせている。
GFX資源DSP69%のままNNを同時搭載できるとは判断しない。NN側はモデルごとの固定回路より、
積和・行列積・畳み込み・活性化・量子化を共通演算器として設計し、必要モデルの演算/メモリを見積もる。
LINKとバッファ/メモリ管理の下位契約は共有する。現GFXへDDRは未統合であり、共通DDR接続は今後の実装。
ビットストリーム切替では描画用回路が外れる。同時実行は別途資源・帯域・実機計測が合格した組合せだけとする。
