# RT-DETR RQG2とNPU4E24の互換性・RTL試験（2026-11-07）

結論：確認したRQG2の57 Conv・65 MatMul/Gemmの形状と静的INT8配置は、既存4E24の0x68/0x78へ分割して表現できる。追加した代表RTL試験は369コマンドに合格し、production RTL修正・新bitstream・書込みは行っていない。RT-DETR全モデルの実機推論が成功したという結果ではない。

## 参照版と型付き重み

carrierの[4E24固定版](NPU_4E24_MatMul_統合検証_2026-11-07.md)、host `rtdetr_graph.hpp/.cpp`、RQG2 `build/rtdetr-graph-300-quant/{metadata.bin,manifest.json}`、static RQW export、backend担当のmapping案を照合した。RQG2 package SHA256は `775b42010c82da0d464db21812563122539b090bc236af7c610eba0f1257d251`、metadataは `5dd82c9740f47f4c58cbfc4af910fccb8c07b7025b7a926a26017e332eda0210`。これは本監査時点の固定入力で、将来再exportした版へ無条件に適用しない。

649ノード中のMAC演算は57 Conv、61 MatMul、4 Gemmの計122操作。静的binding114件（57+53+4）、動的MatMul8件。これはDeiTの122batchesという数字とは別である。typed bindingはINT8 OC×K /N×K、OC pitch=align16(K)、per-output FP32 scale。ConvのKはIC×KH×KW。payload上の位置は `QuantizedBinding.data_offset/scale_offset` を使い、元RQW header64B等を再加算しない。removed FP32 MAC tensorのaddressは無効なので、FLOAT tensorとして読み直したりCPU fallbackしたりしない。

独立metadata parser `python fpga/npu/tests/audit_rtdetr_shapes.py` で全bindingのpitch・span・alignmentと形状を確認した。57 Convはk3s1が27、k1s1が24、k3s2が6、すべてgroup1/dilation1、対称pad0/1。非対応group/dilationを黙って別演算にしない。MM最大M8400/K1024/N1024はいずれもjob幅制約内。Gemm4件はM400または300、K=N256、transA0/transB1、alpha=beta1である。

動的8 MatMulは8 headsのQK/AVで、400tokensまたは300tokens。各headのB baseを保持し、headをまたいで同じBと仮定しない。静的rank2 Bに対するAのleading dimensionsをMへ畳む最適化は、per-logical-row A量子化ならscaleと数値を維持できる。global-A-per-batch量子化へ同じ変形を無条件適用するとpolicyが変わる。backend担当はper-row policyと動的head保持を確認している。

payloadはINT8 weight19,858,432B、scale103,328B、non-MAC constants706,656Bを含む。旧FP32最終版はconstant+arena131,758,368Bでworkspace余裕が約2.46MBしかなく、今回のworkspace根拠には使わない。旧packed歴史版148,927,968Bは容量超過の資料であり、現在版と混ぜない。

最大Conv qinputは3,276,800B（例512×80×80）。M8400/K256のMatMul qAはalign16(M)×K等を予約し、M panel分baseをずらす際の保守的なK×A_pitch spanを後続領域へ侵入させないguardも確保する。temp CはM≤256/N≤8 jobなら8,192B。scratch残量だけでallocation/liveness実装を認定せず、backendの実際のpool終端・alias・leaseを検証する。

後述32MiB/80MiBはアドレスbit経路の試験用windowで、実モデルのallocation案ではない。実配置の静的weightはconstant payload内、workspaceはscratch先頭以降である。32MiBを無条件にweight置き場へ決めるとarenaと競合し得る。

## ConvとMatMulのmapping

Convはqinput NCHW、row pitch=align16(W)、channel pitch=row×H。OC8/IC16/spatial≤16へ分け、weight_base=qB+OCbase×fullOCpitch+ICbase×KH×KW、weight_OC_stride=fullOCpitch。input_base=qinput+ICbase×channelpitch、origin=(output tile origin×stride−pad)。IC0だけfirst、最後だけfinalとする。同じtileのIC途中でgeometry・OC baseを変更しない。Cは専有8,192Bの範囲にrow pitch64、channel pitch=OH×64で書く。OWに合わせた16B書込み尾部は所有し、pitch gapを保存する。

Gemm/MatMulはqA[K,align16(M)]とstatic NxK bindingまたは動的8列slabを0x78へ渡す。M panel offset、N尾部、K尾部を保持し、0x78 Nはそのjob内のNとする。INT32 CをP4でdequant/biasする現段階のhookで、FP32 epilogueが4E24へ組み込まれたとは扱わない。

## 代表RTL検証

`python fpga/npu/tests/run_rtdetr_ddr_contract.py` は未変更4E24のSYS/core/sequencer/loader/8OC/arbiter/bridge/adapterを使う。native DDRだけを疎なbyte-memoryモデルにし、32MiB・80MiB・128MiB上端のAPP_ROW_PAD逆変換を確認する。入力/静的weightは固定seedの合成INT8 fixtureであり、学習済みRT-DETRの推論品質を試すものではない。

| ケース | 検証出力 |
|---|---:|
| IC32/OC9、k3s2p1、19×23→10×12、OI pitch288 | 1,080 |
| IC33/OC9、同形状、OI pitch304、最終IC1 | 1,080 |
| IC256/OC9、k1s1、3×5、OI pitch256 | 135 |
| Gemm M3/K65/N9、OI pitch80 | 27 |
| Gemm M257/K65/N9、M256+1・N8+1 | 2,313 |

追加分はConv2,295値、MM2,340値が独立INT64 oracleと一致した。最初の2 IC block後にCが未公開のままか、OC/IC尾部、M padding、16B尾部zero、output guardとpitch gapを照合した。元の4E24数値・CRC・session/cal-loss・timeout・reset/ARM試験も保持し、全369コマンドに合格した。

初回実行は新しい高address Convが既存TBの低address recovery用descriptor cacheを上書きし、旧fixture再開部分で失敗した。この試験側cacheを低address専用へ限定した。production RTL変更はなく、失敗logと理由も保存した。確定試験は `fpga/build/npu-rtdetr-contract-final`。

[検証アーカイブ](../fpga/validation/npu-rtdetr-4e24-contract-2026-11-07/checkpoint.json)には新script、metadata shape audit、RTL結果/TB、失敗履歴、SHAを保存した。9個の実RTL source SHAは元4E24 build archiveと完全一致する。model payload/metadata本体・巨大vectors/vvp・新FSは追加していない。

## 待ち時間・復帰と未検証範囲

0x68は1tile完了まで待つ。最大通常tileのengineはOH16×OW16×(2×IC16×3×3+3)=74,496 cycles（約2.76ms）で、upload/DDR/制御時間は別。0x78は1panel全体の完了待ちで、hostは4E24専用bounded60秒、endpointは実accepted/completed進捗だけで更新する1秒watchdog。busy/ready highを進捗にはしない。controllerの異常長期stallではこのwatchdogやdrain/quarantineへ移るため、平均値で最悪待ちを保証しない。

全57 Convの既定分割は217,280 tile、25,155,993,600 MAC。既存engine counter式から計算だけで6,416,947,200 cycles、27MHzで約237.665秒と見積もる。これはloader・DDR・host wire・P4演算を含まない。Conv qinput upload合計48,087,040B、Conv FP32出力171,008,000Bもあるため、全モデル試験は数分以上を許容し、live FPSやCPU超えを約束しない。実測値ではない。

RT-DETR backendは全体で4E24 capabilityを要求する。4E23にもlegacy Convはあるが0x78がないため、復帰後にRT-DETR matrix backendを自動継続しない。主担当が既知の4E24 FSを明示書込みし、USER/CAPS・session・CRC selftestを確認してから試験する。abort/校正喪失はframe全体を無効にし、協調resetと再bind・必要データ再uploadで回復する。既存STA未認定条件も維持する。

本監査で互換性は示せたが、全649-node graphのdevice数値、typed package upload、計算時間、検出品質、長時間再利用はbackend/主担当の実機試験待ちである。P4が非MAC演算を処理する段階であり、画像→全NN FPGA内部→結果だけという最終構成は引き続き別段階となる。
