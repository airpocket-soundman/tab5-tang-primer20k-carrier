# DDR3 clk400 sys27 -> user100 の限定SDC例外案（未検証）

作成日: 2026-11-04 / 状態: **提案のみ。ビルドで効果を確認するまで、例外が有効・妥当とは扱わない。**
対応ファイル: `fpga/mem/config/mem_bist_clk400_scoped.sdc.proposal`（既存 `mem_bist_clk400.sdc` + 限定例外）

## 1. 背景と結論の要約

- clk400構成は memory 398.25MHz（27MHz x 59/4）、USER = memory/4 = 99.5625MHz。27MHzと99.5625MHzは整数比でなく、最近接エッジ距離は0.628ns（レポートの Relation 列）。81MHz構成（27->81 は 1:3）では出なかった違反が、sys27 -> user100 に出る。
- 対象レポート: `fpga/build/mem-variant-clk400_notap/out/mem_bist/impl/pnr/mem_bist_tr_content.html`（Gowin V1.9.11.03 Education、使用SDCは `fpga/build/mem-scheduler-diag-input-clk400/mem_bist.sdc`）。
- 主な発見:
  1. 違反は IP内部（controller/...）だけではない。**自作ロジック `control/held_op*` -> USER側レジスタ**の違反が、表示された setup 25本のうち19本（76%）を占める。これは既存の held_base/count/seed/job 向け `set_max_delay 20` に **held_op が含まれていない**ことによる制約漏れで、IP例外では扱えず、同じ契約（2 USER周期以上安定）をholdバンドルに追加する形で扱うべき（案E4）。
  2. recoveryは大半（246/256）が IP内の `ddr_rsti_reg_2`（IP同期リセット、fanout 約3000）起点。残りは自作の reset_hold / mailbox_epoch -> リセット同期器のCLEAR。
  3. レポートは打切りされており、**全違反は列挙できていない**（5章）。
  4. `set_clock_groups -asynchronous` は使わない。GowinではSUG940 3.8の優先度が「max/min_delay < false_path < clock_groups」なので、clock_groupsは既存の `set_max_delay`（held/snapshot）を黙って無効化してしまう。

### 2.3 その他のレポート値

- user100 setup TNS = -176.618、違反endpoint数 308（`Endpoints TNS` 表）。表示された25本は全て -6.27 以下なので、**残り283 endpointは -6.27 より浅い**。ここは未分類。
- 推測（未確認）: 308のうち相当数は `user_snapshot`(512) / `user_debug_snapshot`(176) / `user_deep_snapshot`(256) のCE/Dで、`held_op` デコード由来の自作ロジックと考えられる。IP内部ばかりとは限らない。
- ヘッダの「Numbers of Setup Violated Endpoints = 4018」は308と一致せず、意味（recoveryやmin pulse等の合算か）を確認できていない。**未解決の不一致として残す。**
- hold違反は0（Numbers of Hold Violated Endpoints = 0）。
- 既存の限定例外（`set_max_delay`4本、`set_false_path`95本）はレポートのタイミング制約表で全て Actived。`get_pins {controller/...}` 形式の指定が通ることは実績がある。

## 3. Gowin SDCの対応状況（SUG940-2.0.5J より）

- `set_false_path`: `-from/-through/-to` の少なくとも1つが必須。`-from/-to` は get_clocks/get_ports/get_regs/get_pins、`-through` は get_nets/get_pins。`-setup` は **setup と recovery** に、`-hold` は **hold と removal** に有効（省略時は4種すべて）。したがって recovery だけを個別指定するオプションはなく、`-setup` を使う。
- `get_regs` はFFのみ。ワイルドカード `?`/`*` が使え、`*` は階層をまたぐ。既存SDCの `control/held_base*` と同じ書き方で動作実績あり。
- `set_clock_groups -asynchronous|-exclusive -group ...` はクロック単位のみ。レジスタ単位の限定は不可。
- 優先度（低->高）: create_clock/generated < derive_clocks < multicycle < max/min_delay < **false_path** < **clock_groups**。同一パスで競合する場合のみ効く。よって false_path の対象に `set_max_delay` 済みのパスが含まれると、max_delayが無効になる。案ではfalse_pathのfrom/toをそれらと重ならないレジスタ名に限った。
- 未確認: `-from [get_regs]` と `-to [get_clocks]` の混在。構文表は両方を許可しているが組合せは文書に例がない。案では実績のある regs/pins 指定のみを使った。

## 5. 理由と未確定リスク

### E1（IP内部）
- 根拠: IPUG281-2.6J 4.4.3 は rst_n を **clk（27MHz）で同期解放**してからIPに入れる設計とし、IP内のSync_modが pll_lock 待ちの後に `ddr_rst` を出す。`ddr_rsti_reg_*` はその同期リセット（clk側）で、リセット解放は一度きりの準静的事象。Sipeedサンプルの SDC は clk と clk_x1/clk_x4 を非同期宣言しており、ベンダ自身が同種経路を検査対象外にしている。
- **正当化できない点**: IPがclk(27MHz)ドメインとclk_out(user)ドメインのリセット解放をどう調停しているか、IPUGの図・文面だけでは確認できない。`ddr_rsti_reg_2`（fanout約3000）が user側のFFのD/CEに直接入る（setup 1番の `cmd0_mem DI[0]`）ことは、解放がuserエッジの窓に入ると1サイクルだけ状態が分裂し得ることを意味する。リセット解放はキャリブ前に1回だけで、以後 `ddr_init_st` の遷移が起きるまでタイマ類が動き続けるため、実害は初期化の再試行で吸収される可能性があるが、**実機で冷起動を繰り返して確認するまで安全とは言えない**（既存の複数seed soak手順を使う）。
- `ddr_sync_ddr_init_st -> u_ddr_init_timer_cnt0 D/CE` は準静的な初期化状態フラグがカウンタのCE/Dに入る形で、フラグ遷移はmsオーダのタイマ待機の前後でしか起きない。ただしこれも「静的だと思われる」の域を出ない。
- ワイルドカードの兄弟レジスタ（`ddr_rsti_reg_0/1`、他の `ddr_sync_*`）が同じ性質かは、表示分に無いため**未検証**。広げ過ぎを避けるため、他のIPレジスタ起点は列挙された後に追加する。

### E2（reset_hold -> IP）
- `controller_reset_n = raw_reset_n && pll_lock && reset_hold==0` は sys_clk のレジスタ（reset_hold）の比較結果で、解放は sys_clk に同期。IPUG281 4.4.3 の「rst_n は clk で同期解放」を満たす。IP内でrst_nが user側CLEARに直接入っても、IP内部の同期化は前提どおり。
- 非同期にアサートされるのは raw_reset_n（外部ポート）で、これは本例外の対象外（別経路）。
- 懸念: `reset_hold` の解放が user100 エッジの回復時間内に入った場合のIP側 `ddr_init_internal_r` 等の挙動は、IPが想定する範囲かどうか文書で確認できていない。

### E3（自作リセット同期器）
- `user_reset_sync` と `epoch_reset_sync` はともに「非同期アサート・3段同期解放」。同期器1段目のCLEAR recoveryはメタ安定を許容する設計で、後段は前段出力がリセット中は0のため同値。既存SDCの `*_sync_0/D` のfalse_pathと同じ考え方。
- `user_async_reset_n` にはIP出力 `ip_user_reset`（USERドメイン）も入る。これは例外の from に含めず、タイミング検査を維持した。
- 追加した `control/mailbox_timeout*`, `control/reset_loss*` は表示分に出ていない**推測による追加**。実際のレポートに現れなければ削除する。

### E4（自作 held_op）
- `held_op` は `held_base` 等と同じSYSサイクルで書込まれ（`mem_mailbox.v` 157行目付近）、`request_toggle` を2段同期した後にUSER側が参照する。保持契約は既存のheldバンドルと同じ。**false_pathではなくmax_delay 20（余裕0.09ns）で縛る**ことで、既存の「バンドルは時間制約付きで通す」方針に合わせる。
- 余裕0.09nsはほぼゼロ。データ遅延4.7～5.0ns（レポート値）に対して20ns制約は十分だが、20nsは契約の理論下限（20.09ns）に近いため、制約を満たしても余裕が小さい点は既存のheld_*と同じ弱点。
- これは自作ロジックの制約漏れの修正であり、IP例外とは区別して扱う。RTL（`mem_mailbox.v`）の変更は伴わない。

### 共通のリスク
- 例外はタイミング検査を無効にするだけで、元の経路が実際に安全になるわけではない。
- ワイルドカードが想定外のレジスタに一致すると、検査対象が減る。`-from` を sys27ドメインの起点レジスタ名に限定しているが、`controller/*` を `-to` に使うため、user100同士の同一ドメイン経路には影響しない（起点が27MHz側のレジスタに限られるため）。ただし起点レジスタが同一ドメインに駆動するパスがあればそれも対象になる。
- 例外が当たったかどうかは、ビルド後のレポート（5章）と制約表で確認する必要があり、この文書の分類は表示された25+256本に基づく。

## 6. 検証手順（gw_shビルド。本案作成時には実行していない）

1. 変種ビルド用のSDCとして `mem_bist_clk400_scoped.sdc.proposal` を `.sdc` に写して使う（既存の `prepare_variant.py` のSDC差替え機構を使う。既存ファイルは本案で変更していない）。
2. ビルド後、`mem_bist_tr_content.html` で次を確認する。
   - タイミング制約表（TC_FALSE_PATH / TC_MAX_DELAY）の追加行が全て Actived であること。Invalid や空一致があれば、そのワイルドカードは何にも一致していない。
   - 追加した `report_timing -setup -from_clock sys27 -to_clock user100 -max_paths 2000 -max_common_paths 1` と同 `-recovery` に **負のスラックが残らない**こと。残る場合、その起点/終点を分類表に追加して再検討する（例外を足す前に分類する）。
   - 逆向きの `user100 -> sys27`（snapshot）の slack が従来どおり 60ns 制約を満たすこと。
   - Hold 違反が 0 のままであること。
   - `Fmax` 表の user100 が 99.5625MHz を満たすか。満たさなくても、今回の例外は同一ドメイン（user100 -> user100）の違反を隠さない。
3. 打切りの有無: setup は既定25本、recovery は256本（`-max_paths 256`）。既定のままでは全違反が見えない。本案は `-max_paths 2000` を足した。recoveryが2000でも打ち切られる場合は、さらに大きくするか `-from` を分けて実行する。
4. 実機確認（冷起動複数seed soak）はビットストリームが出て通過してからの話で、この例外が実機で安全かどうかの根拠にはビルドだけでは足りない。
