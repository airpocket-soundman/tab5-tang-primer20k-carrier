# 引継ぎ資料（2026-11-05、更新版）

`docs/引継ぎ_2026-11-04.md`（GPU側のDMA・転送の最適化、実機の基準線）の続き。**2026-11-05 の進捗**と、現在のmainの状態をまとめる。実機で確認していないことは「未検証」と書いた。方針・企画は `docs/DDR3_方針決定_旧IPを採用_2026-11-05.md`、`docs/企画メモ_大型YOLOをDDR3常駐で動かす_2026-11-05.md` を参照。

## 1. main の状態
- キャリア（FPGA）main：DDR3（旧IP＋自前ロジック、`MEMV1` プロトコル、帯域測定エンジン）、CRC slice-by-8、キャリア用cst生成、compute-simd、NPU見積もり、実機試験キュー、各種記録を統合済み。
- ホスト（ESP-IDF）main：`integrate-host-2`（CRC、モデル常駐ホスト経路、中間周波数・クロック駆動・エッジ読出し、DMA最適化のopt-in、実機回帰済み）、`memv1-host`、`mem-bw-host`、`tab5-pipeline`（`host_prefill`、単体ベンチ）を統合済み。
- 旧IP（Sipeedサンプル、Gowin製の暗号化IP）を含むビットストリームは、再配布条件が未確認のため **mainに入れていない**（`fpga/validation/sampleip-bitstreams-excluded.md`）。手順は `docs/DDR3_旧IP保管と再現手順_2026-11-04.md`。

## 2. DDR3（最優先事項。実機で動作）
| 項目 | 結果 |
|---|---|
| 旧IP＋自前ロジック（`sampleip_map_t4`、USERCODE 0x0233） | パターン10、境界6、規模4（128MiB全域）、全域×8 seed、10分soak（96ジョブ）すべて合格 |
| `MEMV1`（`mem_v1_top`、USERCODE 0xA692） | CAPS、STATUS（診断語7＝0x01bb）、RD 1／256ビート（4096B）、WR（CRC32付き）、CRC32、不正要求14種と CRC不一致5種の拒否、末尾4KiB、CANCEL（WR完了後に届き `wr_completed_cancel_dropped`）がすべて合格 |
| 帯域（`t4_bw2`、USERCODE 0xAF） | シーケンシャル 書込み511.6／読出し513.6 MB/s（理論1593MB/sの約32%）、読出し遅延337ns、行ミス・バンク回転で150〜200MB/s。旧BIST推定（約51MB/s）の約10倍。バースト（`--burst`）は未測定 |
| 再生成IP（新ツール） | 400MHz系5種は校正が完了せず、324MHz系は校正は通るがBISTが停止（コマンドFIFO満杯、スケジューラが取り出さない）。2Tは生成不可。**ペンディング**。再開契機：別版のIP生成器、またはGowin／Sipeedの回答 |

- 初版の `MEMV1` イメージが校正できなかった原因は、準備スクリプトがPLL分周 `IDIV_SEL=3` を落としたこと（`PA1019`／`TA1123` で検出可能。検査を追加済み）。
- **opcode衝突：** 帯域測定（0x60〜0x6F）と `MEMV1`（0x60〜0x67）が重なる。別イメージで使い、同居させない。回避案は帯域測定を 0x70〜0x7F へ移すこと（RTL変更は未実施）。
- ホストからの転送はGPIOリンク（500kHz以下）で、4KiBの片道に約1.3秒。**転送の高速化（PARLIO＋DMA、高速応答経路）が次の課題**（`claude/memv1-dma-design` で設計中）。
- 実機の手順（概要）：イメージをSRAMに書込み（`programmer_cli`、cable-index 1）→ MEM probeファーム（`claude/mem-bw-host` 以降、`xferx`／`bw` 対応）を書込み → `tools/memv1_xfer.py`、`tools/probe_mem_bw.py`、`tools/mem_stage_runner.py`。各ツールのヘルプと `docs/memv1-host.md`、`docs/mem-bw-host.md`（ホスト）を参照。
- 限界：冷起動の繰返し、温度、電源条件は未実施。STAは診断用SDC（3クロックを非同期扱い）の下で違反0（最悪setup +0.02〜0.08ns）、IP内部のクロック間パスは検査していない。物理容量（1Gbit）とサンプルの「ビット26での容量判定」の整合は未解決。

## 3. GPU側（Tab5パイプライン）
- `host_prefill`（バッファ事前クリアの省略、`link action=host_prefill`、既定OFF）：実機で描画が約3〜5%短縮（−18〜34ms）、全画素一致。**既定ONにするかは未決定（ユーザーの判断待ち）。**
- Tab5単体ベンチ（`-StandaloneBench`、コンソールをUSB Serial/JTAGにしたベンチ専用イメージ）：PPA fillはCPU memsetの約3.8倍速（1.36ms 対 5.2ms）、タイル組立はPPAがCPUより約2.6倍遅い（CPUのまま）、模擬の2コアパイプラインは約6%。PARLIOの項目はパッド未指定でスキップ。
- 未実施：ポリゴンのモデル常駐（B・K）の実機検証、25MHz以上の切り分け（J：エッジ数カウンタ、N：応答位相）、CRC高速化の実機比較（実施中、結果は別途）、J・N・B・Lのmain統合（`link_bringup_filtered.v` の衝突、実機検証後）。

## 4. 実機の扱い（このPC）
- JTAG：Gowin `programmer_cli`（`fpga/build/tools/gowin-programmer-1.9.12.04/...`、Git管理外）、`--cable-index 1`。書込み後の「Error found!」は既知（USERCODE・Statusで確認）。openFPGALoaderはFTDIドライバの都合で使えなかった。
- Tab5：`esptool` を ESP-IDFのPython環境で、COM4。ESP-IDFのビルドは **PowerShell から**（Git Bash では MSYSTEM のため失敗する）。
- イメージ：`D:\esp\images\` にローカル展開（Git管理外）。基準線は `baseline_85bac224`、DDR3は `p2_sampleip_map_t4`、`memv1\`、`membw\`。
- このPCでは Codex も動いている。COM4／JTAGの競合に注意。
